# Canonical Representation Patterns in Existing Systems

**Research ticket:** [#5 — Research universal canonical representation patterns](https://github.com/davidlinnnn/data-ingestion/issues/5) (wayfinder:research)
**Date:** 2026-08-22
**Method:** Primary sources only — official specifications, first-party documentation, and source code. Every claim carries a citation to the source that owns it. No secondary write-ups were used.

**Question under test:** How do existing canonical/intermediate representations structure a universal Asset / Revision / Element / Relationship model with typed payloads across documents, structured records, APIs, and multimodal content? Which primitives do they treat as core vs extensible, how do they version and attach enrichment, and how do they avoid (or fall into) lowest-common-denominator flattening?

---

## 1. Executive summary

Sixteen models were examined across four families: document-understanding models (Docling, unstructured.io, Azure Document Intelligence, Apache Tika), content/knowledge interchange standards (W3C PROV, DCAT 3, schema.org, JCR, DITA, HL7 FHIR), data-catalog/lineage models (OpenLineage, Egeria, OpenMetadata), and multimodal/layout standards (ALTO, PAGE XML, IIIF Presentation + W3C Web Annotation).

**The hypothesis is well supported, with one crucial refinement.** No surveyed model achieves universality by defining one rich schema that covers every source family. Every durable model instead converges on the same architecture: a **small, closed, universal envelope** (identity, type label, containment, position, provenance) combined with a **governed mechanism for typed, named, schema-referenced payload attachments** — OpenLineage calls them facets ([spec](https://openlineage.io/docs/spec/facets/)), FHIR calls them extensions ([spec](https://hl7.org/fhir/extensibility.html)), Egeria calls them classifications ([docs](https://egeria-project.org/reference/)), JCR calls them mixin node types ([spec §3.7.5](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)), Docling calls them meta fields and annotations ([source](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)). The universal part is deliberately thin; the typed part is deliberately open. This is exactly the Asset/Revision/Element/Relationship + typed-payload shape the HLD proposes.

**The overlay hypothesis has strong precedent.** IIIF is the purest expression: a Canvas is a blank coordinate space and *all* content — including the primary image — is attached by annotation, with the `painting` motivation marking content that is *of* the source and `supplementing` marking content (explicitly including OCR and transcription) that is *derived from* it ([IIIF Presentation 3.0 §5.3](https://iiif.io/api/presentation/3.0/)). PAGE XML ships multiple competing transcriptions per region (`TextEquiv` with an `index`) and derived images (`AlternativeImage`) alongside the source coordinates ([schema](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)); Docling stores model-generated descriptions with per-prediction `created_by` and `confidence` on the item without touching the source content ([source](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)).

**Lowest-common-denominator flattening is the defining failure mode of exactly the two models that lack the envelope+payload split.** Apache Tika normalizes over a thousand formats into a single XHTML event stream plus a flat metadata map ([Parser docs](https://tika.apache.org/3.3.0/parser.html)) — uniform, but structure beyond XHTML's vocabulary is gone. unstructured.io emits a flat list of elements whose hierarchy survives only as inferred `parent_id`/`category_depth` metadata and whose tables are stringified into an HTML metadata field ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). The models that avoid flattening do so by *not* requiring a universal payload: DITA lets every specialized element declare its ancestry so processors can degrade gracefully instead of rejecting or discarding ([spec](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/specialization.html)); FHIR states that extensions carry "no stigma" precisely so the core can stay simple ([spec](https://hl7.org/fhir/extensibility.html)).

**Recommendation in one line:** keep the four primitives; make the Element an envelope with per-family typed payloads (never a merged super-schema); model Revision as an immutable snapshot DAG with three separate version axes (schema, content, enrichment); implement overlays as standoff, named, producer-attributed, schema-referenced attachments bound to a specific Canonical Revision; and treat containment/reading-order as privileged native relationships while reifying qualified relationships as typed objects. Details in §4.

## 2. Per-model analysis

Each model is assessed on six dimensions: **(a)** core primitives, **(b)** typed extensibility, **(c)** versioning/revision, **(d)** source fidelity vs flattening, **(e)** attachment of derived/enriched content, **(f)** relationships (native vs inferred).

### 2.1 Document-understanding models

#### Docling — `DoclingDocument`

- **(a) Core primitives.** A `DoclingDocument` holds content items in typed top-level lists (`texts`, `tables`, `pictures`, `key_value_items`) and structure in two trees rooted at `body` and `furniture` (headers/footers), with reading order encoded by child order in the `body` tree ([concepts](https://docling-project.github.io/docling/concepts/docling_document/)). The base classes form a three-level hierarchy: `NodeItem` (identity + tree position: `self_ref` JSON pointer, `parent`, `children`, `content_layer`), `DocItem` (adds a `label` enum and provenance list), and `FloatingItem` (adds `captions`, `references`, `footnotes`, `image`) ([source: items/node.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/items/node.py)).
- **(b) Typed extensibility.** Item payloads are typed pydantic subclasses (e.g., `TableItem`, `PictureItem`, `CodeItem`). The `meta` structure has standard typed fields (`summary`, `language`, `entities`, `keywords`, `topics`, `description`, `classification`) and allows custom fields only in the validated form `namespace__field_name` — unnamespaced custom keys are rejected ([source: common/meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)).
- **(c) Versioning.** The document itself carries `schema_name: "DoclingDocument"` and a semver-constrained `version` field defaulting to the library's `CURRENT_VERSION`, i.e. the *format* is versioned; there is no revision model for content instances ([source: document.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py)).
- **(d) Fidelity.** Every `DocItem` carries `prov: list[ProvenanceItem]` with `page_no`, `bbox`, and `charspan` — "a lightweight pointer back into the original document" ([source: common/reference.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/reference.py)). Body vs furniture separation preserves the distinction between main content and page apparatus ([concepts](https://docling-project.github.io/docling/concepts/docling_document/)).
- **(e) Enrichment.** Optional pipeline steps (code understanding, formula understanding, picture classification, picture description) write results onto the target item; picture descriptions land in `picture.meta.description`, and API usage payloads can be preserved in namespaced custom meta (`docling__usage`) ([enrichments docs](https://docling-project.github.io/docling/usage/enrichments/)). Every prediction field carries optional `confidence` and `created_by` (the producing model id) ([source: common/meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)).
- **(f) Relationships.** Containment is native (parent/children `RefItem` JSON pointers). Cross-references are explicit refs: floating items point to their captions/footnotes; `FineRef` extends a ref with a span range for fine-grained targets ([source: common/reference.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/reference.py), [items/node.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/items/node.py)). No inferred semantic relationships live in the model.

#### unstructured.io — element taxonomy

- **(a) Core primitives.** Partitioning returns "a list of document `Element` objects"; every element has a `type` from a fixed taxonomy (`Title`, `NarrativeText`, `ListItem`, `Table`, `Image`, `Header`, `Footer`, `Formula`, `CodeSnippet`, …), an `element_id`, extracted `text`, and a `metadata` object ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)).
- **(b) Typed extensibility.** The taxonomy is closed; variability is absorbed by the metadata bag, which has per-filetype fields (e.g. `page_name` for Excel sheets, email headers for EML) and per-connector `record_locator` fields ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). There is no user-defined element typing.
- **(c) Versioning.** None at the model level. The default `element_id` is "a SHA-256 hash of the element's text, its position on the page, page number it's on, and the name of the document file" — deterministic, but any text change produces a new identity; UUIDs are opt-in ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)).
- **(d) Fidelity.** This is the flattening case study. The output is a flat list; document hierarchy is demoted to metadata: "`parent_id` may be used to infer where an element resides within the overall hierarchy of a document," aided by `category_depth` ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). Table structure is not modeled as cells but serialized: the raw text lands in `text` and the "HTML representation of the table will be available in the element metadata under `element.metadata.text_as_html`" ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). Coordinates are preserved (`points` + named coordinate `system`), so spatial fidelity survives even though structural fidelity is lossy.
- **(e) Enrichment.** Chunking produces `CompositeElement` objects that *replace* the original elements in the output; the original identities survive only via the `orig_elements` metadata field, and `image_base64` "is not preserved in the output" after chunking ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). Enrichment and representation are entangled rather than layered.
- **(f) Relationships.** Only inferred containment (`parent_id`) and continuation flags (`is_continuation`). No typed cross-references.

#### Azure AI Document Intelligence — layout `AnalyzeResult`

- **(a) Core primitives.** The result is layered over one string: "The top-level content property contains a concatenation of all content elements in reading order. All elements specify their position in the reader order via spans within this content string" ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)). Layers: `pages` (words, lines, selection marks), `paragraphs` (with functional `role`: title, sectionHeading, pageHeader, footnote, …), `tables` (cells with row/column indices, spans, header kinds), `figures`, `sections`, `styles`, `languages`, and semantic `documents` with typed fields ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)).
- **(b) Typed extensibility.** The layout vocabulary is fixed, but the semantic layer is schema-driven: a document type "describes documents sharing a common set of semantic fields, represented by a structured schema, independent of its visual template," with typed field values (string, date, currency, address, arrays, objects) and per-field normalization and confidence ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)).
- **(c) Versioning.** API-versioned models (`apiVersion`, `modelId` on the result); no content revision concept ([AnalyzeResult class](https://learn.microsoft.com/en-us/python/api/azure-ai-documentintelligence/azure.ai.documentintelligence.models.analyzeresult?view=azure-python)).
- **(d) Fidelity.** High, via *dual anchoring*: every element has both `spans` (character offset/length into `content`, in user-perceived grapheme clusters by default) and `boundingRegions` (page number + polygon), with regions arrays handling elements that cross pages ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)). Bounding regions for figures/tables "cover only the core content and exclude associated caption and footnotes" — caption association is modeled, not baked into geometry ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)).
- **(e) Enrichment.** Style and language detection are standoff layers: "a style element describes the font style to apply to text content… specified via spans into the global content property," each with confidence; multiple non-conflicting style objects may cover the same text ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)). Cropped figure images are separately addressable artifacts (`/analyzeResults/{resultId}/figures/{figureId}`) ([layout docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)).
- **(f) Relationships.** Hierarchy is expressed by reference, not nesting: each section's `elements` array holds JSON-pointer-like ids ("/paragraphs/0", "/sections/1"), so the same paragraph objects participate in a flat list *and* a tree; figures reference their related paragraphs and carry a `caption` object with its own `elements` ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)).

#### Apache Tika — Parser / Metadata / XHTML model

- **(a) Core primitives.** One method: `parse(InputStream, ContentHandler, Metadata, ParseContext)`. "The parse method takes the document to be parsed and related metadata as input and outputs the results as XHTML SAX events and extra metadata… the XHTML format is used here only to convey structural information, not to render the documents for browsing" ([Parser interface docs](https://tika.apache.org/3.3.0/parser.html)).
- **(b) Typed extensibility.** The `Metadata` object is a key-value map passed "both in and out of the parser" ([Parser docs](https://tika.apache.org/3.3.0/parser.html)). `TikaCoreProperties` "contains a core set of basic Tika metadata properties, which all parsers will attempt to supply (where the file format permits)… defined in terms of other standard namespaces," so that users "can have consistent metadata across file formats… no matter if one file format calls it Title, another Long-Title and another Long-Name" ([TikaCoreProperties javadoc](https://tika.apache.org/3.3.0/api/org/apache/tika/metadata/TikaCoreProperties.html)). This is a *shared metadata vocabulary*, not a typed payload mechanism.
- **(c) Versioning.** None; Tika is a streaming extractor, not a store.
- **(d) Fidelity.** The canonical LCD case. All thousand-plus formats are projected into XHTML's element vocabulary plus the flat metadata map. Anything XHTML cannot say — cell-level table semantics, bounding geometry, element identity, per-element provenance, figure/caption association — is gone by construction. The design goals were streamed parsing and simplicity, not fidelity ([Parser docs](https://tika.apache.org/3.3.0/parser.html)).
- **(e) Enrichment.** Not modeled; the output is transient events.
- **(f) Relationships.** Only what XHTML nesting expresses.

### 2.2 Content/knowledge interchange standards

#### W3C PROV-DM (provenance)

- **(a) Core primitives.** Three node types — Entity, Activity, Agent — plus a small set of relations: `WasDerivedFrom`, `WasGeneratedBy`, `Used`, `WasAttributedTo`, `WasAssociatedWith`, `ActedOnBehalfOf`, `WasInformedBy`, `SpecializationOf`, `AlternateOf`, `HadMember` ([PROV-DM](https://www.w3.org/TR/prov-dm/), §2 and Table 4).
- **(b) Typed extensibility.** Everything can carry attribute-value pairs; subtyping via `prov:type` extends both node types and relations ("a revision is a special kind of derivation"), and the spec has explicit extensibility points (§6) ([PROV-DM](https://www.w3.org/TR/prov-dm/)).
- **(c) Versioning.** Revision is not a primitive but a *derivation subtype*: "A revision is a derivation for which the resulting entity is a revised version of some original" ([PROV-DM §5.2](https://www.w3.org/TR/prov-dm/)). `SpecializationOf`/`AlternateOf` distinguish an abstract thing from its fixed snapshots — the exact Asset-vs-Revision distinction.
- **(d) Fidelity.** N/A (PROV describes lineage, not content), but *bundles* — "a named set of provenance descriptions, and is itself an entity, so allowing provenance of provenance" — show how to version the metadata layer itself ([PROV-DM §2.2.2](https://www.w3.org/TR/prov-dm/)).
- **(e) Enrichment.** The Generation/Derivation/Attribution triple is the reference vocabulary for binding an enrichment overlay to the revision it was computed from and the agent (model) that produced it.
- **(f) Relationships.** Core relations are binary; "some advanced uses… require relations to be expanded to n-ary relations" — the qualified-relation reification pattern that DCAT reuses ([PROV-DM §2.2.1.2](https://www.w3.org/TR/prov-dm/)).

#### W3C DCAT 3 (data catalogs)

- **(a) Core primitives.** `Catalog`, `Resource`, `Dataset`, `Distribution`, `DataService`, `DatasetSeries`. "`dcat:Distribution` represents an accessible form of a dataset such as a downloadable file"; `dcat:Resource` "is actually an extension point for defining a catalog of any kind of resources" ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)).
- **(b) Typed extensibility.** Subclassing the Resource extension point plus *application profiles* (DCAT-AP and its national/geo/statistical derivatives) that add constrained properties on top of the base vocabulary ([DCAT 3, "DCAT profiles"](https://www.w3.org/TR/vocab-dcat-3/)).
- **(c) Versioning.** DCAT 3 added first-class versioning: `dcat:version`, `dcat:previousVersion`, `dcat:hasCurrentVersion`, `dcat:hasVersion` (specializing `dcterms:hasVersion`), plus `DatasetSeries` for evolving collections ([DCAT 3 §11–12](https://www.w3.org/TR/vocab-dcat-3/)).
- **(d) Fidelity.** The Dataset/Distribution split keeps the abstract asset separate from its concrete serializations — the spec notes that "many existing and legacy catalogs do not distinguish between dataset components, representations, documentation, schemata and other resources that are lumped together as part of a dataset" ([DCAT 3 §6.4.15 usage note](https://www.w3.org/TR/vocab-dcat-3/)), i.e., the absence of this split is a recognized failure mode.
- **(e) Enrichment.** Out of scope, delegated to PROV (DCAT reuses `prov:` qualified terms).
- **(f) Relationships.** Standard Dublin Core relations where they fit, and reification where they don't: `dcat:qualifiedRelation` links "to a description of a relationship with another resource… used… where the nature of the relationship is known but does not match one of the standard properties," range `dcat:Relationship`, sub-property of `prov:qualifiedInfluence` ([DCAT 3 §6.4.15](https://www.w3.org/TR/vocab-dcat-3/)).

#### schema.org

- **(a) Core primitives.** A multiple-inheritance type hierarchy under `Thing` with properties whose `domainIncludes`/`rangeIncludes` allow several types — "purely pragmatic… in practice [single domain/range] forces the creation of a lot of artificial types" ([data model](https://schema.org/docs/datamodel.html)).
- **(b) Typed extensibility.** Multi-typing is legal and encouraged: "something might simultaneously be both a Book and a Product and be usefully described with properties from both types" ([data model](https://schema.org/docs/datamodel.html)).
- **(c) Versioning.** The vocabulary itself is release-versioned; instance versioning is not modeled.
- **(d) Fidelity / failure mode.** Conformance is deliberately loose — "in the spirit of 'some data is better than none', search engines will often accept this markup"; the type system knowingly over-generates ("the schemas for Volcano suggest that since volcanoes are places, they may have fax numbers") ([data model](https://schema.org/docs/datamodel.html)). This shows the cost of loose polymorphism as a canonical contract: flexible ingestion, unenforceable guarantees for consumers.
- **(e) Enrichment.** Not layered; later claims overwrite or sit beside earlier ones with no producer attribution.
- **(f) Relationships.** The `Role` pattern reifies qualified relationships without changing the property vocabulary: "a Role can be used to say that a 'member' role linking some SportsTeam to a player occurred during a particular time period… attached to a Role entity, which is then associated with the main entities using ordinary properties" — the Role interposes on the same property name (`member` → Role → `member`) and adds `roleName`, `startDate`, `endDate` ([schema.org/Role](https://schema.org/Role)).

#### JCR / JSR-283 (Java Content Repository 2.0)

- **(a) Core primitives.** A workspace is a tree (graph, with the optional shareable-nodes feature) of nodes and typed properties; property types are `STRING, URI, BOOLEAN, LONG, DOUBLE, DECIMAL, BINARY, DATE, NAME, PATH, WEAKREFERENCE, REFERENCE` ([JCR 2.0 §3](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).
- **(b) Typed extensibility.** "Every node has one declared primary node type and zero or more mixin node types. Primary node types are typically used to define the core characteristics of a node, while mixin node types are used to add additional characteristics" — "in effect, mixin node types permit per instance node type inheritance," assignable during a node's lifetime ([JCR 2.0 §3.7.1.4, §3.7.5](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)). Standard mixins (`mix:title`, `mix:created`, `mix:lastModified`, `mix:language`, `mix:mimeType`, `mix:referenceable`) are reusable capability grants. `nt:unstructured` exists as an explicit free-form escape hatch ([JCR 2.0 §3.7.13.1](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).
- **(c) Versioning.** Opt-in per node via a mixin (`mix:versionable` / `mix:simpleVersionable`). "When a versionable node is checked-in, a new version… contains a (typically partial) copy of its subgraph," scoped by each item's on-parent-version attribute; versions live in a version history "which contains a version graph that records the position of each version in relation to its direct predecessor and direct successor versions," with multiple predecessors "thus forming a merge within the version graph"; checked-in state is read-only until check-out ([JCR 2.0 §3.13](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).
- **(d) Fidelity.** Content modeling is left to node-type design; the spec's contribution is that *structure, typing, and versioning are one model*, including frozen nodes that snapshot state and even relax referential integrity for historical references ([JCR 2.0 §3.8.2, §3.13.3.7](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).
- **(e) Enrichment.** Via mixins adding properties/child nodes to existing instances without changing their primary type ([JCR 2.0 §3.7.5](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).
- **(f) Relationships.** Containment is privileged (the tree); cross-tree links are typed properties with declared integrity semantics: `REFERENCE` "properties do enforce referential integrity," `WEAKREFERENCE` "do not" ([JCR 2.0 §3.6.1.11–12](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)).

#### DITA 1.3 (topic-based technical content)

- **(a) Core primitives.** Topics and maps, with a fixed base element vocabulary per module.
- **(b) Typed extensibility.** *Specialization*: "the creation of new element types and attributes that are explicitly and formally derived from existing types," which "ensures a minimum level of common processing for all DITA content" ([DITA 1.3 §2.5.3](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/specialization.html)). Every element declares its full ancestry: "The specialization hierarchy of each DITA element is declared as the value of the `@class` attribute… All specialization-aware processing can be defined in terms of `@class` attribute values" ([class attribute rules](https://docs.oasis-open.org/dita/dita/v1.3/errata01/os/complete/part1-base/archSpec/base/specialization-class-attribute.html)).
- **(c) Versioning.** Not instance-level; the mechanism of note is *round-tripping*: the `@class` default "MUST NOT be fixed," so generalized content can be re-specialized ([class attribute rules](https://docs.oasis-open.org/dita/dita/v1.3/errata01/os/complete/part1-base/archSpec/base/specialization-class-attribute.html)).
- **(d) Fidelity / anti-flattening.** *Generalization* is the explicit, lossless fallback: "Generalization is the process of reversing a specialization… Specialized content can be generalized to any ancestor type. The generalization process can preserve information about the former level of specialization to allow round-tripping" ([DITA 1.3 §2.5.4](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/generalization.html)). This is the strongest surveyed answer to LCD flattening: consumers that don't know a type can still process it *as its ancestor*, and nothing is thrown away.
- **(e) Enrichment.** Not applicable (authoring format).
- **(f) Relationships.** Maps and relationship tables hold inter-topic links outside topic content; content reuse is by reference (`conref`/`keyref`) ([DITA 1.3 Part 1](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/specialization.html)).

#### HL7 FHIR R5 — extensibility model (added candidate)

Included because it is the most battle-tested typed-extensibility contract in production interchange.

- **(b) Typed extensibility.** "Extensibility is a fundamental part of the design… Every element in a resource can have extension child elements… Applications should not reject resources merely because they contain extensions" ([FHIR Extensibility](https://hl7.org/fhir/extensibility.html)). Every extension is schema-anchored: its `url` "SHALL be a reference to the canonical URL of a StructureDefinition that defines the extension"; extensions are simple (one `value[x]`) or complex (nested extensions) ([FHIR Extensibility](https://hl7.org/fhir/extensibility.html)).
- **(d) Anti-flattening rationale.** "Incorporating all valid requirements would make this specification very cumbersome… there can be no stigma associated with the use of extensions… The use of extensions is what allows the FHIR specification to retain a core simplicity for everyone" ([FHIR Extensibility](https://hl7.org/fhir/extensibility.html)). I.e., the core is *deliberately* the common denominator, and fidelity lives in governed extensions — the denominator is not "lowest" because nothing is discarded.
- **(f) Safety valve.** `modifierExtension` marks extensions that change the meaning of their container, so consumers know what they cannot safely ignore ([FHIR Extensibility](https://hl7.org/fhir/extensibility.html)).

### 2.3 Data-catalog / lineage models

#### OpenLineage

- **(a) Core primitives.** Exactly three: Job ("a process that consumes or produces Datasets… This is abstract"), Run ("an instance of a Job that represents one of its occurrences in time"), Dataset ("an abstract representation of data… unique name within a namespace derived from its physical location") ([object model](https://openlineage.io/docs/spec/object-model)).
- **(b) Typed extensibility.** Everything else is a facet: "an atomic piece of metadata identified by its name… attached to the core entities" ([facets](https://openlineage.io/docs/spec/facets/)). Facets are governed: custom facets "must use a distinct prefix named after the project defining them"; each has a `_schemaURL` that "must be an immutable pointer to the version of the facet schema"; and "custom facets can be promoted to the standard by including them in the spec" ([facets](https://openlineage.io/docs/spec/facets/)).
- **(c) Versioning.** Facet schemas are individually versioned via `_schemaURL`; update semantics are replace-by-name: "Emitting a new facet with the same name for the same entity replaces the previous facet instance for that entity entirely" ([facets](https://openlineage.io/docs/spec/facets/)). A standard `version` dataset facet captures store-native versions (e.g. Iceberg snapshot id) ([object model](https://openlineage.io/docs/spec/object-model)).
- **(d) Fidelity.** The model deliberately distinguishes what is stable from what is per-occurrence: "metadata that is more static from Run to Run is captured in a DatasetFacet… What changes every Run is captured as an InputFacet or an OutputFacet" ([object model](https://openlineage.io/docs/spec/object-model)).
- **(e) Enrichment.** Facets *are* the enrichment mechanism (schema, data quality metrics, statistics), attached without touching the core entity.
- **(f) Relationships.** Lineage edges are not stored as first-class links; they are *derived* from Run events referencing input/output Datasets — "a lineage graph can be created by weaving together observations of many Jobs" ([object model](https://openlineage.io/docs/spec/object-model)).

#### Egeria (ODPi open metadata)

- **(a) Core primitives.** Three instance kinds: "Entities — the principle nodes in the metadata graph…; Relationships — links (edges)…; Entities can also be decorated with classifications" ([open metadata instances](https://egeria-project.org/concepts/open-metadata-instances/)). Types are governed by `EntityDef` / `RelationshipDef` / `ClassificationDef` TypeDefs ([type definitions](https://egeria-project.org/concepts/open-metadata-type-definitions/)).
- **(b) Typed extensibility.** The type system "is deliberately comprehensive to maximize the opportunity of seamless metadata exchange… also extensible" ([reference](https://egeria-project.org/reference/)). Classifications are the overlay primitive: "a classification provides a means to extend an entity with additional facets of information: for example, describing the level of confidentiality" ([reference](https://egeria-project.org/reference/)); each classification instance "can only connect to a single entity" ([instances](https://egeria-project.org/concepts/open-metadata-instances/)).
- **(c) Versioning.** TypeDefs themselves carry version numbers and provenance (`origin`, `createdBy`, `createTime`) ([type definitions](https://egeria-project.org/concepts/open-metadata-type-definitions/)).
- **(f) Relationships.** The strongest relationship typing surveyed: "RelationshipDefs include details of the entity type that may be attached at End 1… and End 2" ([type definitions](https://egeria-project.org/concepts/open-metadata-type-definitions/)); relationships identify their ends by `EntityProxy`, are "directional, identifying a starting end (end 1) and a finishing end (end 2)… can be navigated in either direction" ([instances](https://egeria-project.org/concepts/open-metadata-instances/)); a RelationshipDef also declares whether "multiple relationships of this type are allowed between the same two entities" and "the rule that determines if classifications are propagated across this relationship" ([RelationshipDef API](https://odpi.github.io/egeria/org/odpi/openmetadata/repositoryservices/connectors/stores/metadatacollectionstore/properties/typedefs/RelationshipDef.html)).

#### OpenMetadata

- **(a) Core primitives.** Schema-first JSON Schema entity definitions for each asset kind, connected by relationships; every change is recorded with a `changeDescription` ("Change that leads to this version of the entity") ([high-level design](https://docs.open-metadata.org/v1.11.x/api-reference/main-concepts/high-level-design)).
- **(b) Typed extensibility.** Custom properties are declared per entity *type* with a typed `propertyType` (string, integer, date, entityReference, enum, …) and config; values are stored in the entity's `extension` attribute ([custom properties](https://docs.open-metadata.org/v1.13.x/developers/custom-properties)).
- **(c) Versioning.** The most concrete instance-versioning policy surveyed: "OpenMetadata maintains the version history for all entities using a number with the format major.minor, starting with 0.1… Backward compatible changes result in a Minor version change (0.1 → 0.2)… Backward incompatible changes result in a Major version change. For example, when a column in a table is deleted, the version increases by 1.0 (0.2 → 1.2)" ([versioning docs](https://docs.open-metadata.org/latest/how-to-guides/guide-for-data-users/versions)). Compatibility-classified revisioning tells consumers whether re-materialization is needed — directly reusable for Canonical Revision semantics.

### 2.4 Multimodal / layout standards

#### ALTO (Library of Congress)

- **(a) Core primitives.** Strict physical hierarchy: root `alto` → `Description` (measurement units, source image info, `OCRProcessing` history), `Styles`, and `Layout` → `Page` → margins + `PrintSpace` → `TextBlock` → `TextLine` → `String` ([structure](https://www.loc.gov/standards/alto/techcenter/structure.html), [element set](https://www.loc.gov/standards/alto/techcenter/elementSet/)).
- **(b) Typed extensibility.** Little; styles are factored out and referenced by `STYLEREFS` IDREFs ([element set](https://www.loc.gov/standards/alto/techcenter/elementSet/)).
- **(c) Versioning.** The *schema* has an explicit compatibility policy: whole-number versions for breaking changes, decimals otherwise, and "the namespace itself will also only change on major versions" ([ALTO standard page](https://www.loc.gov/standards/alto/)).
- **(d) Fidelity.** Positions on every element (`HPOS`, `VPOS`, `WIDTH`, `HEIGHT`), page quality flags, and OCR confidence in-band: `String` carries `WC` (word confidence, 0–1) ([layout docs](https://www.loc.gov/standards/alto/techcenter/layout.html)).
- **(f) Relationships.** Reading order became explicit only in v4.3: "Add support for explicit reading order definitions with 'ReadingOrder' element containing 'UnorderedGroup's, 'OrderedGroup's, and 'ElementRef's" ([ALTO standard page](https://www.loc.gov/standards/alto/)) — evidence that implicit document-order eventually proves insufficient.

#### PAGE XML (PRImA)

- **(a) Core primitives.** Page → typed regions (text, image, table, …) with polygon `Coords`, nested regions, and an explicit `ReadingOrder`: "To express a reading order between elements they have to be included in an OrderedGroup. Groups may contain further groups," with confidence ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)).
- **(e) Enrichment — the standout feature.** Multiple alternative transcriptions coexist per element: `TextEquiv` may repeat, with an `index` "used for sort order in case multiple TextEquivs are defined. The text content with the lowest index should be interpreted as the main text content," each with its own `conf`; and derived images (binarized, deskewed) attach via `AlternativeImage` (filename + comments + confidence) without replacing the source image ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)). This is versioned enrichment overlays, in-file.
- **(d) Fidelity.** Dual text encodings per equivalent (`PlainText` vs `Unicode`, the latter "correct encoding of the original, always using the corresponding Unicode code point") ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)).

#### IIIF Presentation API 3.0 + W3C Web Annotation

- **(a) Core primitives.** Collection → Manifest → Canvas → AnnotationPage → Annotation, plus Range. A Canvas is "a virtual container… The concept of a Canvas is borrowed from standards like PDF and HTML… where an initially blank display surface has images, video, text and other content 'painted' on to it by Annotations" ([IIIF 3.0 overview](https://iiif.io/api/presentation/3.0/)).
- **(e) Enrichment — the reference design.** *All* content, source and derived alike, attaches by annotation; motivation distinguishes them: `painting` content "must be presented to the user as the representation of the Canvas. The content can be thought of as being of the Canvas"; `supplementing` content "can be thought of as being from the Canvas," with OCR named explicitly: "Content that is derived from the Canvas, such as a manual or automatic (OCR) transcription of text in an image… must be associated by an Annotation that has the motivation value supplementing" ([IIIF 3.0 §5.3, motivations table](https://iiif.io/api/presentation/3.0/)). "The same mechanism is used for the visible and/or audible resources as is used for transcriptions, commentary, tags… As Annotations can be added later, it promotes a distributed system in which publishers can align their content with the descriptions created by others" ([IIIF 3.0 §2](https://iiif.io/api/presentation/3.0/)).
- **(b) Typed extensibility.** Extensions add properties via JSON-LD scoped contexts and a community registry; "clients must ignore motivation values that they do not understand" ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)).
- **(f) Relationships.** Structure is overlay too: Ranges group Canvases "for content-based reasons, such as might be described in a table of contents," and Ranges with `behavior: sequence` "represent different orderings of the Canvases listed in the `items` property of the Manifest" — multiple simultaneous structures over the same content ([IIIF 3.0 §5.4, behaviors](https://iiif.io/api/presentation/3.0/)).
- **Targeting model (Web Annotation).** "An Annotation is a rooted, directed graph that represents a relationship between resources" (bodies and targets) ([Web Annotation Data Model §2](https://www.w3.org/TR/annotation-model/)). Sub-resource targeting uses a SpecificResource with Selectors — FragmentSelector, CSS, XPath, TextQuoteSelector (`exact`/`prefix`/`suffix`), TextPositionSelector (`start`/`end`), DataPosition, SVG (non-rectangular areas), Range — with *refinement* allowing selectors to be combined, which in practice provides redundant anchoring that survives drift in any single coordinate system ([Web Annotation Data Model §4.2](https://www.w3.org/TR/annotation-model/)).

## 3. Cross-cutting patterns and anti-patterns

### Patterns (what the successful models converge on)

**P1 — Thin universal envelope, typed open payloads.** Every model that spans heterogeneous content keeps the universal layer to identity + type-tag + structure + position, and pushes richness into governed typed attachments: OpenLineage's three core entities + facets ([facets](https://openlineage.io/docs/spec/facets/)), Egeria's entity/relationship/classification triad ([reference](https://egeria-project.org/reference/)), FHIR's resources + extensions ([extensibility](https://hl7.org/fhir/extensibility.html)), JCR's nodes + primary/mixin types ([JCR §3.7](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)), Docling's `NodeItem`/`DocItem` envelope + typed items and meta ([source](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/items/node.py)), DCAT's `Resource` extension point + profiles ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)).

**P2 — Extensions are governed, not free-form.** The attachment mechanism is always named, namespaced, and schema-referenced: OpenLineage facets carry an immutable versioned `_schemaURL` and project-prefixed names, with a promotion path from custom to standard ([facets](https://openlineage.io/docs/spec/facets/)); FHIR extension `url`s must resolve to a canonical StructureDefinition ([extensibility](https://hl7.org/fhir/extensibility.html)); Docling rejects custom meta keys that aren't `namespace__field_name` ([meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)); OpenMetadata custom properties are typed declarations on the entity type, not ad-hoc keys ([custom properties](https://docs.open-metadata.org/v1.13.x/developers/custom-properties)). Tika shows the alternative — an ungoverned key-value map rescued only by a curated core-property vocabulary ([TikaCoreProperties](https://tika.apache.org/3.3.0/api/org/apache/tika/metadata/TikaCoreProperties.html)).

**P3 — Abstract asset ≠ concrete rendition ≠ snapshot.** DCAT separates Dataset from Distribution and warns against catalogs that lump them ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)); PROV separates the general entity from its specializations (`specializationOf`) and revisions ([PROV-DM](https://www.w3.org/TR/prov-dm/)); JCR separates the live versionable node from immutable frozen versions ([JCR §3.13](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); IIIF separates the Canvas (coordinate space) from content resources painted onto it ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)). The HLD's Asset / Source Revision / Canonical Revision chain is this pattern.

**P4 — Derived content is standoff annotation, never in-place mutation.** IIIF motivations (`painting` vs `supplementing`) ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)); PAGE's indexed `TextEquiv` alternatives and `AlternativeImage` ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)); Azure's style/language layers as spans over an untouched content string ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)); Docling's meta predictions with `created_by`/`confidence` ([meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)); Egeria classifications ([reference](https://egeria-project.org/reference/)).

**P5 — Versioning has three independent axes.** (1) *Format/schema version*: `DoclingDocument.version` ([document.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py)), ALTO's namespace policy ([ALTO](https://www.loc.gov/standards/alto/)), OpenLineage `_schemaURL` per facet ([facets](https://openlineage.io/docs/spec/facets/)). (2) *Content revision*: JCR's version graph with predecessors/successors and merges ([JCR §3.13](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)), PROV Revision ([PROV-DM](https://www.w3.org/TR/prov-dm/)), DCAT `previousVersion` chains ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)), OpenMetadata's compatibility-classified major.minor ([versions](https://docs.open-metadata.org/latest/how-to-guides/guide-for-data-users/versions)). (3) *Derived-artifact version*: producer + model identity per prediction (Docling `created_by`), facet replacement by name (OpenLineage). Models that conflate these axes were not found — the separation appears to be load-bearing.

**P6 — Anchor positions redundantly, at multiple levels.** Azure pairs character `spans` with `boundingRegions` and logical `elements` references ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)); Docling's `ProvenanceItem` combines `page_no` + `bbox` + `charspan` ([reference.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/reference.py)); Web Annotation allows selector refinement and multiple selector kinds for the same target ([annotation model §4.2](https://www.w3.org/TR/annotation-model/)). Single-coordinate anchoring (pure char offsets or pure geometry) does not survive re-parsing or revision.

**P7 — Relationships come in three tiers, and reading order is explicit.** Tier 1: containment as the privileged native structure (JCR tree, Docling body tree, ALTO hierarchy, Azure sections). Tier 2: typed references with integrity semantics (JCR `REFERENCE` vs `WEAKREFERENCE` ([JCR §3.6](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); Docling caption/footnote refs). Tier 3: reified relationship objects when the link itself needs properties — schema.org `Role` ([Role](https://schema.org/Role)), `dcat:Relationship` via `qualifiedRelation` ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)), Egeria `Relationship` instances with typed ends, cardinality, and classification-propagation rules ([Egeria](https://egeria-project.org/concepts/open-metadata-instances/)). Reading order is never left implicit at scale: ALTO added a `ReadingOrder` element in 4.3 ([ALTO](https://www.loc.gov/standards/alto/)), PAGE has ordered/unordered groups ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)), Azure orders the global content string ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)), and IIIF Ranges can define alternative orderings over the same canvases ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)).

### Anti-patterns (observed failure modes)

**A1 — Lowest-common-denominator flattening.** Two mechanisms produce it:
1. *Projection into a fixed poor vocabulary.* Tika maps every format into XHTML events + a metadata map ([Parser docs](https://tika.apache.org/3.3.0/parser.html)); whatever XHTML cannot express is silently dropped, and there are no element identities or provenance anchors to recover it.
2. *Demoting structure to metadata.* unstructured keeps a flat element list and moves hierarchy into inferred `parent_id`/`category_depth` metadata and tables into a `text_as_html` string ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)). Structure that lives in a metadata bag is not part of the contract: consumers cannot rely on it, validators cannot check it, and enrichment cannot target it.
   The survey's avoidance strategies: keep the core minimal *and lossless* via governed extensions (FHIR: "no stigma… core simplicity" ([extensibility](https://hl7.org/fhir/extensibility.html))); make specialized types degrade gracefully to declared ancestors instead of being discarded (DITA `@class` + generalization round-trip ([spec](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/generalization.html))); layer rather than choose (Azure keeps both the plain reading-order string *and* the structural layers over it ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0))).

**A2 — Loose polymorphism as a contract.** schema.org's own docs acknowledge that pragmatic looseness produces unenforceable data ("some data is better than none"; volcanoes with fax numbers) ([data model](https://schema.org/docs/datamodel.html)). Acceptable for web-scale ingestion by search engines; wrong for a canonical layer that downstream systems must *trust and rebuild from*.

**A3 — Enrichment indistinguishable from source.** ALTO embeds OCR confidence in the source hierarchy itself (`WC` on `String`) ([layout](https://www.loc.gov/standards/alto/techcenter/layout.html)) — workable for a single-producer OCR format, but it cannot represent two competing transcriptions. PAGE (indexed `TextEquiv`) and IIIF (motivations) solve exactly this. A canonical layer that mixes "what the source says" with "what a model said about the source" cannot re-run models without rewriting the core.

**A4 — Identity that does not survive transformation.** unstructured's default `element_id` is a hash of text + position + page + filename ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)), so any revision changes every id; chunking then replaces elements with `CompositeElement`s, keeping originals only inside an `orig_elements` metadata field. Overlays and lineage need ids that are assigned, stable within a revision, and mapped across revisions — not derived from content.

**A5 — Tree-only or flat-only structure.** Flat-only breaks hierarchy (unstructured). Tree-only breaks cross-cutting content: JCR needed the shareable-nodes extension for multi-parent cases ([JCR §3.9](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); Azure's answer — flat typed collections plus structure-by-reference (sections pointing into `/paragraphs/N`) — lets several structures (physical pages, logical sections, tables, figures) coexist over the same elements ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)); IIIF Ranges do the same for alternative orderings ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)).

## 4. Recommendations for the Asset/Revision/Element/Relationship + typed-payload + overlay hypothesis

### Adopt

1. **Keep the four primitives; they match the strongest precedents.** Asset ↔ DCAT Dataset / JCR versionable node / OpenLineage Dataset-by-name; Revision ↔ JCR frozen version / PROV Revision / DCAT version chain; Element ↔ Docling `DocItem` / Azure element; Relationship ↔ Egeria Relationship / JCR reference ([DCAT 3](https://www.w3.org/TR/vocab-dcat-3/), [JCR §3.13](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html), [PROV-DM](https://www.w3.org/TR/prov-dm/), [Egeria](https://egeria-project.org/concepts/open-metadata-instances/)).

2. **Make the Element an envelope + typed payload, with the envelope closed and small.** Envelope: stable id, element-kind label from a small closed set, parent/children refs, order, provenance anchors, governance refs. Payload: per source-family typed schema (document text/table/picture; record/field; API operation/schema; media segment). This is P1 and is precisely how every surveyed model spans heterogeneity. Do **not** attempt one merged element schema with optional fields for all families — no surveyed model does this, and schema.org documents the cost of trying ([data model](https://schema.org/docs/datamodel.html)).

3. **Govern typed payloads and overlays like OpenLineage facets + FHIR extensions.** Each payload/overlay type gets: a namespaced name (project-prefixed), an immutable versioned schema reference (OpenLineage `_schemaURL` ([facets](https://openlineage.io/docs/spec/facets/)); FHIR canonical StructureDefinition URL ([extensibility](https://hl7.org/fhir/extensibility.html))), and a documented promotion path from tenant/team-custom to platform-standard ([facets](https://openlineage.io/docs/spec/facets/)). Enforce namespacing at validation time as Docling does (`namespace__field_name` ([meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py))).

4. **Implement overlays as standoff annotations bound to (Canonical Revision, Element id, optional selector).** Follow IIIF's motivation split: canonical core = "of the source" (painting), overlays = "from the source" (supplementing) ([IIIF 3.0 §5.3](https://iiif.io/api/presentation/3.0/)). Each overlay record should carry: overlay kind, producer + model/version (`created_by` per Docling ([meta.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/meta.py)); Agent/Activity per PROV ([PROV-DM](https://www.w3.org/TR/prov-dm/))), confidence (PAGE/ALTO/Azure all carry it), and the derivation link to the exact canonical revision it was computed from (`prov:wasDerivedFrom`). Use replace-by-(name, target, producer) update semantics as OpenLineage does ([facets](https://openlineage.io/docs/spec/facets/)), and allow multiple ranked alternatives per target as PAGE `TextEquiv/index` does ([XSD](https://www.primaresearch.org/schema/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd)).

5. **Version on three axes, explicitly.** (1) Canonical-schema version stamped on every document/element payload (Docling `version` ([document.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py)); ALTO's breaking-change namespace policy ([ALTO](https://www.loc.gov/standards/alto/))). (2) Content revisions as immutable snapshots forming a DAG — JCR allows multiple predecessors (merge) and freezes checked-in state ([JCR §3.13](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); classify revisions by compatibility as OpenMetadata does (minor = additive, major = breaking, e.g. element deleted) so projections know when rebuilds are mandatory ([versions](https://docs.open-metadata.org/latest/how-to-guides/guide-for-data-users/versions)). (3) Overlay versions independent of both, bound to their source revision. Record lineage in PROV vocabulary (Entity/Activity/Agent, `wasGeneratedBy`, `wasRevisionOf`) so knowledge lineage and future experience lineage share one model ([PROV-DM](https://www.w3.org/TR/prov-dm/)) — this also serves HLD §3.12 (knowledge/execution lineage connectable).

6. **Anchor provenance redundantly.** Every element and overlay target should combine logical anchor (element id / JSON pointer), spatial anchor (page + region polygon), and textual anchor (charspan), as Docling's `ProvenanceItem` and Azure's spans + boundingRegions + elements do ([reference.py](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/common/reference.py), [response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)); Web Annotation's selector-refinement is the general mechanism ([annotation model §4.2](https://www.w3.org/TR/annotation-model/)).

7. **Treat structure as layered references, not one exclusive tree.** Keep elements in flat addressable collections; express body hierarchy, furniture, reading order, tables, and figure groupings as references over them (Azure sections; Docling body/furniture content layers; IIIF Ranges incl. alternative orderings) ([response docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0), [Docling concepts](https://docling-project.github.io/docling/concepts/docling_document/), [IIIF 3.0](https://iiif.io/api/presentation/3.0/)). Make reading order an explicit construct from day one — ALTO retrofitting it in v4.3 is the cautionary tale ([ALTO](https://www.loc.gov/standards/alto/)).

8. **Type the relationships.** Define relationship types with typed ends, cardinality, and directionality à la Egeria `RelationshipDef` ([type definitions](https://egeria-project.org/concepts/open-metadata-type-definitions/)); distinguish integrity-enforced vs weak references à la JCR ([JCR §3.6](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); reify a relationship into an object with properties only when it needs qualification (schema.org Role, `dcat:Relationship`) ([Role](https://schema.org/Role), [DCAT 3](https://www.w3.org/TR/vocab-dcat-3/)). Keep source-native relationships (containment, caption-of, links, foreign keys) in the canonical core; keep *inferred* semantic relationships (GraphRAG entities/edges) in projections — consistent with HLD §5.3 and with the fact that no surveyed canonical model stores inferred semantics in its core.

9. **Adopt a graceful-degradation contract for unknown types.** Require every specialized element/payload type to declare its ancestry to a base kind so generic consumers can process unknown types as their ancestor (DITA `@class`/generalization ([spec](https://docs.oasis-open.org/dita/dita/v1.3/errata01/os/complete/part1-base/archSpec/base/specialization-class-attribute.html))), and require consumers to ignore unknown overlay kinds rather than fail (IIIF: "clients must ignore motivation values that they do not understand" ([IIIF 3.0](https://iiif.io/api/presentation/3.0/)); FHIR: don't reject resources for containing extensions ([extensibility](https://hl7.org/fhir/extensibility.html))). This is the mechanism that lets the model be universal *without* being lowest-common-denominator.

### Avoid

- **Text as the only universal payload; tables/figures stringified into metadata** (unstructured `text_as_html` ([docs](https://docs.unstructured.io/open-source/concepts/document-elements)); Tika XHTML ([Parser docs](https://tika.apache.org/3.3.0/parser.html))). Keep tables as structured cell grids and images as first-class payloads with regions.
- **Structure or governance stored in an untyped metadata bag.** If a consumer must rely on it, it belongs in the typed contract (contrast unstructured's inferred `parent_id` with JCR/Docling's first-class children lists).
- **Content-derived hashes as element identity** (unstructured `element_id` ([docs](https://docs.unstructured.io/open-source/concepts/document-elements))). Assign ids; maintain revision-to-revision correspondence separately.
- **A single mutable "current" document with no frozen snapshots.** Every versioning precedent (JCR check-in, PROV Revision, DCAT versions, OpenMetadata history) relies on immutable revision snapshots.
- **Enrichment writing into source fields** — competing model outputs then require core rewrites; PAGE/IIIF show the standoff alternative.
- **Un-namespaced, un-schema'd custom fields** — the difference between OpenLineage/FHIR-style governed extensibility and an eventual metadata swamp ([facets](https://openlineage.io/docs/spec/facets/), [extensibility](https://hl7.org/fhir/extensibility.html)).
- **Linear-only revision chains.** JCR's version graph supports merges (multiple predecessors) ([JCR §3.13.2.6](https://developer.adobe.com/experience-manager/reference-materials/spec/jcr/2.0/3_Repository_Model.html)); sources with branching histories (wikis, code, collaborative docs) will need the DAG.
