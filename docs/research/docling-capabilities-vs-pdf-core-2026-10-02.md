## Integration facts the comparison must retain

`v2.132.0` changes PDF reading order and adds `use_reading_order_separators` for backends exposing visible rule geometry. Comparing it directly with the pinned adapter would mix an upstream algorithm change with adapter effects; this must be a separate upgrade comparison. [Release](https://github.com/docling-project/docling/releases/tag/v2.132.0), [tagged options](https://github.com/docling-project/docling/blob/v2.132.0/docling/datamodel/pipeline_options.py).

The pinned upstream execution order is build → assemble → enrich. Common picture/chart enrichment models are constructed by `ConvertPipeline.__init__`; code/formula enrichment is added by `StandardPdfPipeline._init_models`. [Pinned base pipeline](https://github.com/docling-project/docling/blob/v2.102.0/docling/pipeline/base_pipeline.py), [pinned standard pipeline](https://github.com/docling-project/docling/blob/v2.102.0/docling/pipeline/standard_pdf_pipeline.py).

Our capture path returns before document assembly when `checkpoint_only=true`. Restore reconstructs assembled pages and overrides `_init_models` to initialize reading order, so it bypasses the standard code/formula setup, while inherited common enrichment construction still exists. Thus neither “all enrichments are lost” nor “just enable their flags” follows from the source. Each proposed feature needs its inputs, initialization, execution stage, persisted output, and replay behavior traced. [Local parser](https://github.com/davidlinnnn/data-ingestion/blob/fe1b283c49c83ad5aeee6808e77b4f25549eba03/src/pdf_processing/parse.py).

The Q04 consumer currently enumerates `body`, `furniture`, `groups`, `texts`, `pictures`, `tables`, `key_value_items`, and `form_items`. Core `v2.96.0` also has `field_regions` and `field_items`. This identifies a comparison-coverage question, not proof that current fixtures contain those fields or lose data. Preserve raw JSON and explicitly account for every populated collection and meaningful field in any future comparison. [Consumer](https://github.com/davidlinnnn/data-ingestion/blob/fe1b283c49c83ad5aeee6808e77b4f25549eba03/tests/pdf_processing/q04/consumer.py), [pinned model](https://github.com/docling-project/docling-core/blob/v2.96.0/docling_core/types/doc/document.py).

Q04 verifies checked durable output, source attribution, graph relationships, fixture-specific structure, and picture-OCR completion. It deliberately retains `quality_accepted=false` and `canonical_accepted=false`. Those checks do not certify every optional upstream feature, all supported document types, or Canonical Acceptance. [Consumer](https://github.com/davidlinnnn/data-ingestion/blob/fe1b283c49c83ad5aeee6808e77b4f25549eba03/tests/pdf_processing/q04/consumer.py), [local contract](https://github.com/davidlinnnn/data-ingestion/blob/fe1b283c49c83ad5aeee6808e77b4f25549eba03/src/pdf_processing/README.md).

## Minimum separate research ticket

Suggested title: **Compare official Docling capabilities with the selected PDF core and identify functional gaps**.

Question: For the PDF corpus and evidence required by the Knowledge Platform, which useful upstream capabilities are already retained, disabled, absent from the pinned release, outside PDF scope, or unverified by our adapter and consumers?

Deliver an evidence matrix, the smallest necessary functional comparisons, and an adoption recommendation. Start from this source audit; do not repeat it or build a new benchmark framework:

1. Freeze the current package/model/options/code identity and one separately named current-stable candidate; distinguish an upgrade delta from enabling an existing pinned feature.
2. Cover native content/reading order/tables, page versus picture OCR, code/formula, figure classification/description, charts, heading depth, and retained document fields; record VLM conversion and schema extraction as separate methods.
3. For each relevant feature, name its input evidence, upstream stage, emitted field/artifact, adapter preservation, and consuming requirement. Mark **available**, **enabled**, **retained**, and **qualified** independently.
4. Reuse the existing source-reviewed PDF fixture inventory and results; run only uncovered paired cases. Compare pinned stock native with the selected method for intentional adaptation deltas, then selected uninterrupted output with checkpoint/restore output for preservation. Compare any chosen new feature or version against its own fresh baseline. Separate custom-continuation/reading-order method changes from checkpoint losses.
5. Record a small source-reviewed acceptance inventory for each proposed addition: heading depth, equations/code meaning, chart values, figure interpretation versus original caption, table cells/spans, graph/provenance, and uncertainty. JSON equality alone is not a source-fidelity oracle.
6. End with **retain / evaluate next / defer / outside scope**, including the minimum follow-up experiment and its required evidence. Keep recovery/resource benchmarking, rollout changes, full-format parity, and broad model surveys in separate work.

Unknowns remain explicit: this research did not execute any optional feature, establish their quality on the corpus, verify every advertised format/backend, certify all latest-stable Core compatibility, or establish the first release of every capability. It supplies a scoped decision artifact and proposed evaluation, not a demand to enable everything Docling offers.

## #70 extension: decision and evidence boundary

**Recommendation:** retain the qualified native PDF method and its supervised parser in a dedicated Activity resource pool. Keep deterministic Workflow workers free of inference execution. Add one private component-inference boundary only when #32 adopts a concrete missing Enrichment; remote picture description is the first bounded candidate, while code/formula is a candidate for a reviewed paper case. Remote mode is already available for more pinned stages than the original audit discussed. A latest-version upgrade, a whole-document service, and all-model offloading are separate choices, each requiring affected validation.

This answers the full [#70 research request](https://github.com/davidlinnnn/data-ingestion/issues/70), read with its complete body and comments, and the [#52 current decisions and qualified handoff](https://github.com/davidlinnnn/data-ingestion/issues/52#issuecomment-5950521498). It supplies recommendations to the pending owners; it does not adopt a canonical schema, close design decisions, publish a deployment, or alter the scope of #33/#46/#51. The authority is #52's confirmed charter and target contracts: Wiki first, Retrieval checks reusability, Paper PDF/SOP Markdown/PPTX inform representation, Kubernetes is the target, Temporal infrastructure is shared, and physical choices remain open. A logical responsibility need not be a separate service. Processing Completion remains distinct from Canonical Acceptance. [#52](https://github.com/davidlinnnn/data-ingestion/issues/52).

**Remote does not mean zero model artifacts:** layout/classification API engines resolve a Hugging Face folder, load `AutoImageProcessor` and `AutoConfig` locally, and may call unfiltered `snapshot_download` for the entire repository. They do not instantiate inference weights, but can still download/cache weight files. Prepackage versioned processor/config artifacts, block unexpected downloads, and measure import/process memory separately before claiming a small container. Imports of Torch/transformers or a method inventory of RapidOCR hashes are not evidence that weights are resident. No automatic local-inference fallback is shown in these explicit API engines; default/auto-inline engines can select local inference and must not be substituted silently. [HF vision helper][hf-vision], [download helper][hf-download], [VLM factory][vlm-factory].

The pinned OCR constructor lacks the `enable_remote_services` parameter/gate used by the VLM/object-detection/classification API engines. Treat the gate as an SDK option, not enforcement of an authorized destination: endpoint allowlisting/network policy and controlled configuration are required for every call. OCR catches per-rectangle exceptions and continues; if OCR is required, a caller must reconcile requested rectangles/components with explicit success/failure outcomes. This is a **source-confirmed adoption risk**, not a defect demonstrated in the currently selected non-KServe method. [OCR implementation][ocr-source], [API engines][layout-api].

### Minimal execution topology and alternatives

**Current physical baseline:** `release.py` renders two Deployments (Workflow/Activity), using the same full image and resource ceilings. The Workflow branch does not initialize Docling inference; the Activity `WORKER_STAGE=all` branch creates six queue pollers (`prepare`, `group`, `assembly`, `select`, `component_ocr`, `finalize`) sharing one `SerialActivities` lock and one `WarmParser`. Six queues are not six physical pools. Stage-specific execution exists, but bootstrap still verifies the full profile/model inventory and can create a parser even for inexpensive stages. [Worker/runtime][worker], [release renderer][release-renderer], [routing][routing].

**Proposed minimum:** use shared Temporal, with Workflow orchestration separate from Activity I/O/inference; retain logical stage queues and co-locate inexpensive compatible Activities by resource class. Put the supervised selected native parser in its own bounded CPU pool; retain local component OCR in a separately placed OCR Activity pool if required to keep inexpensive pools free of OCR weights. This is independent placement without a new inference HTTP service. Thin Workflow/stage images require versioned packaging/bootstrap/inventory changes and startup/resource validation; changing a queue or environment variable alone does not establish that target. Preserve the qualified serial group5 resource budget until #54 chooses and validates a broader envelope. [Supported configuration][supported], [Temporal workers](https://docs.temporal.io/develop/python/workers/run-worker-process).

If one Enrichment is adopted, prefer one optional private model service or model Activity pool shared by compatible component work, not one service per checkbox. The Activity owns source/crop access, durable keyed result, reconciliation and errors; model service owns warm model weights and inference admission. Keep rendering/assembly/crop selection with the parser/component Activity initially; split only if measurements justify it. Maintain a stable result key over source artifact digest + method/model/processor/prompt/config identity + component identity; store result before Activity success. This key identifies a reusable result, **not** a guarantee the provider will execute once.
