# Authorization Model Normalization: What a Hybrid Governance Model Can and Cannot Normalize

**Research ticket:** #10 — Can the hybrid governance model (preserve source policy provenance + normalize into a common enterprise policy model + enforce in every projection and query path) actually normalize what enterprise sources express?

**Scope:** Primary-source analysis of how representative enterprise source families express access policy; which constructs survive faithful normalization into a common policy model; which require preserving source-native semantics; and which established authorization patterns fit query-time enforcement across Vector/Graph/Wiki projections.

**Method note:** All claims below are drawn from official vendor documentation, standards bodies, or peer-reviewed system papers, cited inline. Where a needed fact was *not* found in primary documentation, that gap is stated explicitly rather than filled by inference.

---

## 1. Executive Summary

**The hybrid hypothesis survives contact with the evidence, with one sharpened conclusion: the normalized layer must be a relationship-tuple (ReBAC) model with an attribute/label overlay, and it must be paired with a mandatory "cannot faithfully normalize" escape hatch — because two whole construct classes provably do not flatten.**

1. **Most collaboration-suite policy normalizes cleanly into subject–relation–resource tuples.** SharePoint, Google Drive, Confluence, and Salesforce record-level sharing are all *additive grant* systems: access is the union of grants to users, groups, containers, and hierarchies ([Microsoft Graph permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0), [Google Drive permissions](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions), [Confluence permissions model](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-on-the-page-level/), [Salesforce sharing architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture)). This is exactly the shape of Google Zanzibar's relation-tuple model, which unified ACLs and groups for Calendar, Cloud, Drive, Maps, Photos, and YouTube ([Zanzibar, USENIX ATC '19](https://www.usenix.org/system/files/atc19-pang.pdf)). Salesforce even materializes its own sharing model into per-record share rows plus group-expansion tables internally — independent evidence that tuple materialization of a complex sharing model is viable at enterprise scale ([Record-Level Access: Under the Hood](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)).
2. **Two construct classes cannot be faithfully normalized and must be preserved native.** (a) *Predicate-based row policies* — Snowflake row access policies and PostgreSQL row-level security are arbitrary SQL boolean expressions evaluated per row against live session context and mutable mapping tables ([Snowflake](https://docs.snowflake.com/en/user-guide/security-row-intro), [PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)); flattening them requires materializing per-row × per-principal outcomes, which is a snapshot, not the policy. (b) *Possession-based (link/anonymous) sharing* — SharePoint anonymous links (optionally password-protected and expiring) and Drive `type=anyone` permissions grant access to whoever holds a token, not to an identity ([createLink](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink?view=graph-rest-1.0), [Drive permissions](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)); an identity-keyed policy model has nothing to check at query time.
3. **Deny semantics are rarer than expected but load-bearing where they exist.** Confluence content restrictions narrow space grants ([Atlassian](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/)), Salesforce restriction rules filter already-granted access ([Salesforce](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture)), and Postgres restrictive policies AND onto permissive ones ([PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). A pure union-of-tuples store cannot express these; the normalized model needs an intersection/exclusion layer (Zanzibar/OpenFGA support intersection and exclusion in the model schema; Cedar makes `forbid` override `permit` by construction — [Cedar authorization semantics](https://docs.cedarpolicy.com/auth/authorization.html)).
4. **Classification labels normalize as attributes, not as ACLs.** Microsoft Purview sensitivity labels are persistent clear-text metadata whose *enforcement* (encryption usage rights, sharing-scope defaults) happens at consumption time — Microsoft 365 Copilot returns labeled content only if the user holds the EXTRACT usage right ([Purview sensitivity labels](https://learn.microsoft.com/en-us/purview/sensitivity-labels)); Azure AI Search evaluates Purview labels at query time against the caller's Entra token ([Azure AI Search document-level access](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)). The same pattern (label taxonomy driving policy) exists in Google Drive Labels ([Drive Labels API](https://developers.google.com/workspace/drive/labels/guides/overview)).
5. **Query-time enforcement across projections is a solved pattern with known trade-offs.** The industry-standard options are: security-filter fields carried in the index (Elasticsearch DLS role queries — [Elastic](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level); Azure AI Search `search.in` filters and native permission filters — [Microsoft](https://learn.microsoft.com/en-us/azure/search/search-security-trimming-for-azure-search)); normalized allow-lists maintained by the indexer (Glean `allowedUsers`/`allowedGroups` plus an identity graph — [Glean](https://developers.glean.com/api-info/indexing/documents/permissions)); or an external ReBAC check service consulted at query time, with three documented integration strategies (search-then-batch-check, local index from a changes feed, list-objects pre-filter — [OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)).
6. **The invariant "no projection may weaken source access policy" is enforceable, but its hardest enemy is staleness, not expressiveness.** Zanzibar names this the "new enemy" problem — applying old ACLs to new content or misordering ACL updates — and solves it with external consistency and snapshot reads bounded by causal tokens (zookies) ([Zanzibar §2.2](https://www.usenix.org/system/files/atc19-pang.pdf)). Every replicated-ACL product carries the same caveat (Azure AI Search: "a timing lag occurs before [the preview] recognizes changes to those access or permission restrictions" — [Microsoft](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)). The platform needs explicit revocation-propagation SLOs and fail-closed semantics, and should pin projection versions to ACL-snapshot versions — which aligns with the HLD's existing versioned-projection design.

**Recommendation in one line:** adopt a three-layer policy object — (1) normalized ReBAC tuples for the additive-grant majority, (2) an attribute overlay for labels, expiries, and deny/restriction predicates evaluated by a policy engine at query time, (3) a per-source native-passthrough escape hatch for row-predicate and possession-based constructs — and make every projection query path call the same decision service, never a per-projection re-implementation.

## 2. Per-Source-Family Policy Capability Analysis

Each source family is analyzed against six dimensions: principals/groups model, inheritance/propagation, deny semantics, link/anonymous sharing, classification labels, and staleness/sync mechanics.

### 2.1 Microsoft SharePoint / OneDrive (Microsoft Graph)

**Principals and grants.** A `driveItem`'s sharing state is a list of `permission` resources. Each carries a `roles` collection (`read`, `write`, `owner`), and identifies grantees via `grantedToV2`/`grantedToIdentitiesV2` (`sharePointIdentitySet`, covering users, applications, and SharePoint site users/groups). Permissions come in two facets: **invitation** permissions (specific users/groups) and **link** permissions (sharing links). Permissions may carry `expirationDateTime` and `hasPassword`. ([Graph permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0))

Underneath Graph's simplified three-role view, SharePoint itself has a lattice of ~33 fine-grained permissions composed into permission levels (Full Control, Design, Edit, Contribute, Read, Limited Access, Approve, Manage Hierarchy, Restricted Read, View Only), with a dependency structure (e.g., View Items depends on Open) and admin-customizable levels. ([Understanding permission levels in SharePoint](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels))

**Inheritance/propagation.** All sites, lists, and items in a site collection inherit the root's permissions by default; owners can break inheritance at any level ("unique permissions"). Critically, *sharing an individual item with someone lacking access auto-breaks inheritance on that item*. ([SharePoint permission levels](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels)) Graph exposes inherited entries via the permission's `inheritedFrom` item reference (not returned for OneDrive for Business/SharePoint document libraries). ([Graph permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0))

**Deny semantics.** None in the sharing model itself — grants are additive. ("Limited Access" is a system-assigned traversal level, not a deny. — [SharePoint permission levels](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels)) Deny-like behavior arrives via sensitivity-label encryption (below).

**Link/anonymous sharing.** `createLink` produces links with scope `anonymous` (no sign-in required, may include people outside the organization; admin-disableable), `organization` (anyone signed into the tenant), or `users` (specific people); links can be `view` or `edit`, can carry passwords (OneDrive personal) and expirations, and `retainInheritedPermissions: false` strips existing inherited permissions on first share. If no scope is specified, *the organization's default link type* is created — meaning the effective policy depends on tenant configuration, not just the API call. ([driveItem: createLink](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink?view=graph-rest-1.0))

**Classification labels.** Purview sensitivity labels are customizable, stored as **clear-text, persistent metadata** on files/emails so third-party systems can read them; one label per item; ordered by priority. Labels can enforce encryption with per-user/group usage rights and durations, apply container-level controls on sites/teams (privacy, external sharing, unmanaged-device access), and set the **default sharing-link type** for a site or document — i.e., labels parameterize the sharing model itself. Deleting a label from the admin portal does not remove enforcement from already-labeled content. Microsoft 365 Copilot honors labels: it returns data from an encrypted item only if the user has the EXTRACT usage right. ([Learn about sensitivity labels](https://learn.microsoft.com/en-us/purview/sensitivity-labels))

**Staleness/sync.** The `driveItem: delta` API tracks item changes with resumable tokens. For permission scanning specifically: by default delta returns sharing information for all changed items even if inherited; `Prefer: hierarchicalsharing` returns sharing at the root of each permissions hierarchy plus explicitly-changed items (with an *empty sharing facet* distinguishing "unique but unshared" from "inheriting"); `Prefer: deltashowsharingchanges` annotates items whose appearance was caused by permission change (`@microsoft.graph.sharedChanged: "True"`), requires the companion headers `deltashowremovedasdeleted, deltatraversepermissiongaps`, and — notably — requires the app to hold **Sites.FullControl.All**. ([driveItem: delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)) Group membership drift is trackable via Graph delta query on `group` resources with `$select=members`, including "sync from now" tokens. ([Graph delta query overview](https://learn.microsoft.com/en-us/graph/delta-query-overview))

### 2.2 Google Drive

**Principals and grants.** Each file/folder/shared-drive has permissions with `type` ∈ {`user`, `group`, `domain`, `anyone`} and `role` ∈ {`owner`, `organizer`, `fileOrganizer`, `writer`, `commenter`, `reader`}. Grantees can be flagged `deleted` (tombstoned accounts). `expirationTime` is settable only on user/group permissions, must be ≤ 1 year out, and folder expiry is limited to `reader` role. `permissionDetails` distinguishes `inherited` vs direct and names the ancestor (`inheritedFrom`, populated for shared-drive items). `inheritedPermissionsDisabled: true` marks items where only direct grants (plus organizers/owners) apply. ([Drive permissions reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions))

**Inheritance/propagation.** Folder permission lists **propagate downward recursively**; moving an item re-propagates from the new ancestor chain. The model is *monotonic*: "Inherited permissions cannot be removed or reduced on any item" — they can only be increased on a child, or adjusted at the ancestor where they originate, or cut off via the limited-access setting. Deleting a permission on a folder revokes equivalent inherited access on children, but direct grants on children persist. ([Manage sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing)) Access is evaluated against the ACL at request time: items have a single constant link keyed by `fileId`, and Drive verifies the authenticated identity against the ACL on each open; revoked/expired principals are removed from the ACL. ([Manage sharing — how file links and access control work](https://developers.google.com/workspace/drive/api/guides/manage-sharing))

**Deny semantics.** None. The only subtractive mechanisms are revoking grants and disabling inheritance. ([Manage sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing))

**Link/anonymous sharing.** `type=anyone` grants world access; `type=domain` grants tenant-wide access; both carry `allowFileDiscovery`, which controls **searchability separately from accessibility** — a file can be reachable by link but excluded from search results. ([Drive permissions reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)) This access-vs-discoverability split matters for RAG: surfacing a link-only file in retrieval results would *make it discoverable*, weakening the source policy even though the user could technically open it.

**Classification labels.** Drive Labels are admin- or user-defined structured metadata (badged taxonomies like Sensitivity: Top Secret/Confidential/Public) used to "classify content to follow an information governance strategy" and to "apply policy," e.g., DLP rules preventing download of Top-Secret-labeled files. Reading label metadata requires both item permission (READER) and label permission (READER). ([Drive Labels API overview](https://developers.google.com/workspace/drive/labels/guides/overview))

**Staleness/sync.** The `changes` collection provides an ordered change log with resumable page tokens; `changes.watch` push notifications signal *that* changes exist but carry no detail — consumers must re-poll `changes.list`. Permission changes surface as file changes (the file resource carries `permissions`/`capabilities`). ([Retrieve changes](https://developers.google.com/workspace/drive/api/guides/manage-changes))

### 2.3 Atlassian Confluence (Cloud)

**Principals and grants.** Three levels: **global permissions** (site-wide, admin-managed), **space permissions** (per-space grants of view/add/edit/delete to users, groups, and *anonymous* users), and **content restrictions** (per-page). Group membership is unioned: revoking a permission from an individual does not help if any of their groups still holds it — "Confluence permissions are additive." ([Confluence permissions structure](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/), [Manage permissions at the content level](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-on-the-page-level/))

**Inheritance/propagation and deny semantics.** Content is open by default within a space, and restrictions *narrow*: "content can only be further restricted from whatever the container is set at. A content item cannot have greater access than its container." ([Manage permissions at the content level](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-on-the-page-level/)) **View restrictions inherit down the page tree** ("If someone can't view a parent content item or folder, they won't be able to view any child content items under it"), while **edit restrictions do not inherit**. ([Change who can find content](https://support.atlassian.com/confluence-cloud/docs/add-or-remove-page-restrictions/)) A view restriction on a page denies even space admins the content (though they can *list* restricted pages and remove restrictions — an administrative escalation path a faithful model must not replicate as read access). Links to restricted content render but yield access-denied; links into spaces the user cannot view are not shown at all. ([Confluence permissions structure](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/))

So Confluence is a *two-phase* model: additive space grants ∩ narrowing content restrictions — union at the grant layer, intersection at the restriction layer.

**Link/anonymous sharing.** Anonymous (not-logged-in) users can be granted space permissions explicitly. ([Confluence permissions structure](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/))

**Classification labels.** No enforcement-bearing classification construct appears in the permissions documentation reviewed here (Confluence "labels" are folksonomy tags, not policy). Treat as absent.

**Staleness/sync.** Space permissions and content restrictions are readable via REST, but the Atlassian documents reviewed here do not document a *permission-change delta feed* comparable to Graph delta or Drive changes. This is a verification item for implementation: absent a delta API, permission sync degrades to re-crawl, and revocation latency is bounded by crawl cadence. (Gap noted from [Confluence permissions structure](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/) and related pages, which describe no such feed.)

### 2.4 Snowflake

**Principals and grants.** Access control combines **DAC** (every securable object has an owning role), **RBAC** (privileges → roles → users), and **UBAC** (privileges directly to users, considered only with secondary roles ALL). The baseline is deny-by-default: "Unless allowed by a grant, access is denied." Roles form a hierarchy in which privileges are **inherited upward** by granting roles to roles; `future grants` pre-authorize objects not yet created. There is "no concept of a 'super-user' or 'super-role'... that can bypass authorization checks." ([Overview of Access Control](https://docs.snowflake.com/en/user-guide/security-access-control-overview))

**Session context is part of the policy.** Authorization depends on the session's *active* primary role plus any activated secondary roles — the same user gets different answers depending on which roles are active. ([Overview of Access Control](https://docs.snowflake.com/en/user-guide/security-access-control-overview))

**Row access policies (the hard part).** A row access policy is a schema-level object containing a SQL boolean expression evaluated **per row at query time**; it can test `CURRENT_ROLE()`/`IS_ROLE_IN_SESSION()` and can join against **mapping tables** whose contents are entitlement data. Snowflake evaluates the expression *with the policy owner's rights* (so queriers never need access to the mapping tables), wraps the protected object in a dynamic secure view, supports nested policies (table policy first, then view policies outward), and evaluates row policies before masking policies. Policy conditions referencing `CURRENT_ROLE`/`CURRENT_USER` return NULL when the object is shared to another account — cross-account identity does not travel. ([Understanding row access policies](https://docs.snowflake.com/en/user-guide/security-row-intro))

**Secure views.** Secure views hide the view definition from non-owners and disable optimizations that could leak filtered data (e.g., predicate reordering enabling division-by-zero probing); Snowflake explicitly recommends, for extremely high-security cases, **materializing data per user/role instead of exposing views** — vendor precedent for the per-audience materialization strategy discussed in §5. ([Working with Secure Views](https://docs.snowflake.com/en/user-guide/views-secure))

**Deny semantics.** None in the grant model (pure additive grants); row access policies act as arbitrary row filters, which subsume deny.

**Link/anonymous sharing; labels.** Not applicable in-kind. (Snowflake object tagging/classification exists but was not needed for this analysis and is not cited.)

**Staleness/sync.** Grants and policy references are queryable (e.g., Account Usage views `ROW_ACCESS_POLICIES` and the `POLICY_REFERENCES` Information Schema function — [row access policies doc](https://docs.snowflake.com/en/user-guide/security-row-intro)); no push notification mechanism for grant changes is documented in the pages reviewed. Mapping-table contents — the actual entitlements — are ordinary table data changing at data velocity, not config velocity.

### 2.5 PostgreSQL

**Principals and grants.** Object owners hold all rights implicitly; other roles need explicit `GRANT`s of per-object privileges (15 kinds: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`, `CREATE`, `CONNECT`, `TEMPORARY`, `EXECUTE`, `USAGE`, `SET`, `ALTER SYSTEM`, `MAINTAIN`); `PUBLIC` grants to every role; group roles bundle membership; `WITH GRANT OPTION` delegates granting, and revoking a grant cascades through chains of re-grants. ACLs are stored as `aclitem` entries (`grantee=privileges/grantor`). Additive, owner-centric, no deny entries. ([PostgreSQL: Privileges](https://www.postgresql.org/docs/current/ddl-priv.html))

**Row-level security (the hard part).** Once `ENABLE ROW LEVEL SECURITY` is set, the table is **default-deny**: rows are visible only where a policy's `USING` expression returns true (with `WITH CHECK` guarding writes). Policies are per-command and per-role; multiple **permissive** policies combine with OR, while **restrictive** policies combine with AND on top — a genuine deny layer. Expressions are arbitrary SQL evaluated per row *with the querying user's privileges*, may consult other tables via sub-SELECTs (with documented race-condition hazards), and are bypassed by superusers, roles with `BYPASSRLS`, and table owners unless `FORCE ROW LEVEL SECURITY`. Referential-integrity checks bypass RLS, creating documented covert channels. ([PostgreSQL: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html))

**Staleness/sync.** Catalogs are queryable; no permission-change feed exists in core (logical decoding of catalog changes is not a supported policy feed). Same materialization caveats as Snowflake.

### 2.6 Salesforce

**Principals and grants — a five-layer additive stack.**
- **Profiles/permission sets** control object-level CRUD and field-level security; "View All"/"Modify All" bypass sharing entirely. ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))
- **Organization-wide defaults (OWD)** set the *most restrictive baseline* per object (Private / Public Read Only / Public Read/Write / Controlled by Parent); every other mechanism only opens access up from there. ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))
- **Role hierarchy** gives users access to records owned by or shared with subordinates; hierarchy access "is derived at runtime" rather than materialized as share records, and can be disabled per custom object via Grant Access Using Hierarchies. ([Apex: Understanding Sharing](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_bulk_sharing_understanding.htm), [Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))
- **Sharing rules** (owner-based and criteria-based — the latter keyed on record field values), **manual sharing**, **teams**, **territory hierarchies**, and **Apex managed sharing** all write additive grants; groups nest up to five levels. ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))
- **Implicit sharing** is built-in and non-configurable: seeing a contact/opportunity/case implies seeing its parent account; account owners get configured access to child records. ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))

**How it is implemented (and why it matters here).** For objects not Public Read/Write, Salesforce materializes access as **access grants** in per-object **Object Sharing tables** (explicit/implicit grants, each row = grantee + record + access level + *row cause*) joined against **Group Maintenance tables** (precomputed group/role/territory expansion, including system-defined `Role` and `RoleAndSubordinates` groups). "For users with multiple access grants to a record, Salesforce uses the most permissive grant." ([Record-Level Access: Under the Hood](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)) An ingestion platform can therefore read *computed* shares (share objects are queryable and documented in the Apex guide with access levels Read/Edit/All — [Understanding Sharing](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_bulk_sharing_understanding.htm)) instead of re-implementing rule evaluation.

**Deny semantics.** **Restriction rules** (up to 2–5 active per object depending on edition) are the exception to the additive stack: they *filter* the records a user was otherwise granted, applying to list views, lookups, reports, search, SOQL, and SOSL — "instead of opening up access to users, they further restrict it." ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))

**Link/anonymous sharing.** **Guest user sharing rules** grant unauthenticated guests access to records matching criteria — Salesforce's own docs carry a strong warning about the exposure. ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))

**Staleness/sync.** Two sharp edges: (1) **manual shares are deleted when record ownership changes** — access evaporates as a side effect of an unrelated-looking edit ([Under the Hood, Scenario 4](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf), [Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture)); (2) role/group/territory changes trigger **sharing recalculation** that can take a long time in large orgs (Salesforce supports deferring it during bulk maintenance), so even the *source's own* materialized ACLs lag its logical policy. ([Under the Hood](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf), [Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture))

## 3. Normalization Feasibility Matrix

Target normalized form assumed below: **subject–relation–resource tuples** (ReBAC; Zanzibar-style `⟨object#relation@user⟩` where user may itself be a userset like `group:eng#member`, enabling nested groups — [Zanzibar §2.1](https://www.usenix.org/system/files/atc19-pang.pdf)) plus **attributes/conditions** on tuples or resources (OpenFGA conditions / SpiceDB caveats, CEL-based — [OpenFGA concepts](https://openfga.dev/docs/concepts), [SpiceDB caveats](https://authzed.com/docs/spicedb/concepts/caveats)).

| Source construct | Verdict | Rationale (cited in §2) |
|---|---|---|
| SharePoint/Drive/Confluence/Salesforce direct user & group grants | **Clean** | Additive identity-keyed grants = positive tuples; nested groups = usersets ([Zanzibar](https://www.usenix.org/system/files/atc19-pang.pdf)) |
| Container/folder inheritance (Drive recursive propagation; SharePoint until broken; Confluence space→page, parent→child view restrictions) | **Clean** | Exactly Zanzibar `tuple_to_userset` ("look up parent, inherit its viewers") ([Zanzibar §2.3.1](https://www.usenix.org/system/files/atc19-pang.pdf)); Drive's "inherited can be increased, never reduced" is monotone union ([Drive sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing)); broken inheritance = item-scoped tuple set snapshot ([SharePoint](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels)) |
| Role hierarchies (Snowflake role DAG; Salesforce role hierarchy; SharePoint site groups) | **Clean** | Role-to-role edges are tuples; Salesforce already materializes hierarchy into group-expansion tables internally ([Under the Hood](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)); Snowflake privileges inherit up the role graph ([Snowflake](https://docs.snowflake.com/en/user-guide/security-access-control-overview)) |
| Tenant/domain-wide grants (Drive `type=domain`; SharePoint `organization` links; Salesforce OWD Public Read Only; Confluence space grant to all logged-in users) | **Clean** | Type-bound public access (`user:*` scoped to tenant) is native in OpenFGA ([type-bound public access](https://openfga.dev/docs/concepts)) |
| Role/permission-level flattening (SharePoint 33-permission lattice & custom levels; Drive 6 roles; Salesforce Read/Edit/All) | **Lossy — acceptable** | Knowledge platform needs the *read* verb; map conservatively (only levels whose permission set includes view/open ⇒ `can_read`). Fidelity loss is one-directional and safe if the mapping never infers read from a level that lacks it ([SharePoint permission levels](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels), [Drive roles](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)) |
| Expiring grants (Graph `expirationDateTime`; Drive `expirationTime` with role/duration constraints) | **Lossy → clean with conditions** | Representable as conditional tuples (CEL time predicate) evaluated at check time ([OpenFGA conditions](https://openfga.dev/docs/concepts), [SpiceDB caveats](https://authzed.com/docs/spicedb/concepts/caveats)); a static tuple without conditions silently over-grants after expiry |
| Deny/restriction overlays (Confluence content restrictions; Salesforce restriction rules; Postgres restrictive policies) | **Lossy — needs intersection/exclusion layer** | Pure union-of-tuples cannot express "granted minus restricted"; model-level intersection/exclusion (Zanzibar userset ops — [§2.3.1](https://www.usenix.org/system/files/atc19-pang.pdf)) or engine-level `forbid` overrides `permit` (Cedar — [authorization semantics](https://docs.cedarpolicy.com/auth/authorization.html)) required; OpenFGA notes `and`/`but not` relations are more expensive to evaluate ([search with permissions](https://openfga.dev/docs/interacting/search-with-permissions)) |
| Classification labels (Purview sensitivity labels; Drive Labels) | **Clean as attribute; enforcement must be query-time ABAC** | Labels are persistent clear-text metadata ([Purview](https://learn.microsoft.com/en-us/purview/sensitivity-labels)); enforcement couples label × user × usage right at consumption (Copilot EXTRACT check — [Purview](https://learn.microsoft.com/en-us/purview/sensitivity-labels); Azure AI Search query-time label evaluation — [doc-level access](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)) |
| Discoverability flags (Drive `allowFileDiscovery`) | **Lossy** | Access ≠ searchability; retrieval surfaces content and thus *is* discovery. Must be modeled as a separate `discoverable` attribute honored by retrieval even where access would pass ([Drive permissions](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)) |
| Anonymous / password / expiring **links** (SharePoint `anonymous` scope; Drive `type=anyone`) | **Must preserve native** | Possession-based capability, not identity: "Users don't need to sign-in to access the content shared with a sharing link" ([Graph permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0)); no identity exists to check at projection query time |
| Salesforce guest user sharing rules | **Must preserve native** (or map to explicit `public` with governance sign-off) | Grants to unauthenticated visitors by criteria ([Platform Sharing Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture)) |
| Snowflake row access policies & secure views; Postgres RLS | **Must preserve native** | Arbitrary per-row SQL over session context (`CURRENT_ROLE`, secondary roles) and mutable mapping tables, evaluated with owner's rights ([Snowflake](https://docs.snowflake.com/en/user-guide/security-row-intro), [Postgres](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)); flattening = materializing a per-row × per-principal snapshot that decays immediately |
| Salesforce criteria-based sharing rules & implicit sharing | **Clean via computed shares** (not via rule re-implementation) | Read materialized share rows + group maintenance state rather than re-evaluating criteria ([Under the Hood](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)); accepts the source's own recalculation lag |
| Sensitivity-label *encryption* (Purview) | **Must preserve native** | Encrypted payloads are unreadable without usage rights; label enforcement survives label deletion in the portal ([Purview](https://learn.microsoft.com/en-us/purview/sensitivity-labels)) — ingest only with explicit rights strategy |

**What the escape hatch must handle** (union of the "must preserve native" rows): (a) content whose effective audience is *computable only per-row/per-session at the source* — exclude from normalized projections, or materialize per-audience slices, or federate the query to the source with the end user's identity; (b) content reachable by *possession tokens* — never treat "anyone with link" as "anyone in tenant"; either model `anonymous`-scope links as `public` (explicit governance decision) or suppress link-derived access from projections entirely; (c) *encrypted* content — ingest only if the ingestion identity holds decryption/EXTRACT rights, and then only with the label carried and enforced downstream.

## 4. Candidate Common Policy Models and Query-Time Enforcement Fit

### 4.1 The candidates

**RBAC (NIST/INCITS 359).** Users→roles→permissions with role hierarchies; the ANSI/INCITS standard model since 2004, revised 2012. ([NIST RBAC project](https://csrc.nist.gov/projects/role-based-access-control)) RBAC alone cannot carry per-resource sharing (a SharePoint item shared to one user is not a "role"), which is why every collaboration source above outgrew it internally. NIST itself documents the RBAC-vs-ABAC tension and attribute extensions. ([NIST RBAC project](https://csrc.nist.gov/projects/role-based-access-control))

**ABAC (NIST SP 800-162).** Authorization by evaluating attributes of subject, object, operation, and environment against policy ([SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)). ABAC is the right shape for *labels, expiries, and restriction predicates*, but as a sole model it makes "list everything user X can read" (the retrieval problem) expensive — you must evaluate predicates over the corpus, which is what OPA partial evaluation exists to mitigate (compiling policies toward linear-time/filterable forms — [OPA policy performance](https://www.openpolicyagent.org/docs/latest/policy-performance/)).

**ReBAC / relationship tuples (Zanzibar; OpenFGA/SpiceDB).** Zanzibar stores ACLs as relation tuples with usersets (nested groups), computes effective access via per-namespace userset-rewrite rules (`computed_userset`, `tuple_to_userset`, combined by union/intersection/exclusion), and provides Check/Expand/Read/Watch APIs. It serves trillions of ACLs at millions of QPS with p95 < 10 ms and >99.999% availability, backing Drive, Cloud, YouTube, etc. ([Zanzibar](https://www.usenix.org/system/files/atc19-pang.pdf), [research.google abstract](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)) Its consistency design directly addresses projection staleness: zookies (opaque causal timestamps) let a client demand evaluation "at least as fresh as" a given content version, preventing both misordered ACL updates and old-ACL-on-new-content — the "new enemy" problem ([Zanzibar §2.2](https://www.usenix.org/system/files/atc19-pang.pdf)). OpenFGA adds CEL-conditioned tuples and contextual (request-scoped) tuples ([concepts](https://openfga.dev/docs/concepts)); SpiceDB's caveats are the same idea ("an elegant way to model dynamic policies and ABAC-style decisions" — [caveats](https://authzed.com/docs/spicedb/concepts/caveats)). Deep group nesting is handled in Zanzibar by a dedicated denormalizing index (Leopard) that flattens transitive group containment — evidence that group expansion is *the* scaling pressure point ([Zanzibar §3](https://www.usenix.org/system/files/atc19-pang.pdf)).

**Policy engines (OPA, Cedar) as the overlay evaluator.** OPA decouples decision from enforcement and evaluates declarative Rego over structured input ([OPA docs](https://www.openpolicyagent.org/docs/latest/)), with partial evaluation to precompute/optimize policies ([policy performance](https://www.openpolicyagent.org/docs/latest/policy-performance/)). Cedar evaluates PARC (principal-action-resource-context) requests with three properties tailor-made for a governance invariant: **default deny**, **forbid overrides permit** ("guardrails that permit policies cannot cross"), and skip-on-error ([Cedar authorization](https://docs.cedarpolicy.com/auth/authorization.html)).

**Fit assessment:** the additive-grant majority (§3 "clean" rows) maps to ReBAC tuples; labels/expiries/restrictions map to conditions and a forbid-overlay; RBAC survives as a *special case* of ReBAC (roles are just relations on a tenant/org object). No single pure model covers all three needs; the hybrid is ReBAC-primary + ABAC-overlay, which is precisely what OpenFGA conditions/SpiceDB caveats operationalize.

### 4.2 How production RAG/search systems enforce at query time

- **Index-embedded allow-lists (filter at retrieval).** Azure AI Search's security-trimming pattern stores principal IDs in a filterable `Collection(Edm.String)` field and applies `group_ids/any(g:search.in(g, 'g1,g2'))` per query; the principal "is just a string" — no authentication is implied by the filter itself. ([Security filter pattern](https://learn.microsoft.com/en-us/azure/search/search-security-trimming-for-azure-search)) Its newer built-in modes bind the filter to real identity: query requests carry the user's Entra token in `x-ms-query-source-authorization`, checked against per-document permission metadata (ADLS Gen2 ACLs/RBAC scopes, SharePoint ACLs), and Purview labels are evaluated at query time against the caller's token and Purview policies. ([Document-level access overview](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview))
- **Role-scoped index queries.** Elasticsearch document-level security attaches a Query-DSL predicate to a role per index (templatable with user details); multiple roles OR together — including the sharp edge that one unrestricted role disables DLS for the user entirely; DLS is intended for read-only accounts. ([Elastic: document and field level security](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level))
- **Connector-normalized permissions + identity graph.** Glean's indexing API attaches a `permissions` object per document (`allowedUsers`, `allowedGroups`, `allowAnonymousAccess`, `allowAllDatasourceUsersAccess`), requires users/groups/memberships to be indexed via identity endpoints first, and exposes an `updatepermissions` endpoint to change ACLs without re-indexing content — an existence proof that heterogeneous source ACLs can be normalized into a common allow-list model good enough to ship a commercial enterprise-search product. ([Glean permissions](https://developers.glean.com/api-info/indexing/documents/permissions), [document model](https://developers.glean.com/api-info/indexing/documents/document-model))
- **External check service at query time.** OpenFGA documents three integration strategies for search: (1) **search then check** — retrieve candidates, then `batch-check`; (2) **local index from the changes feed** — consume tuple changes, flatten/expand, intersect locally, then confirm borderline items with `check`; (3) **list-objects pre-filter** — fetch the user's accessible object IDs and constrain the query. Choice depends on candidate-set size and the user's accessible fraction; the documented Google-Drive-like case (user can access many objects, small fraction of corpus) points to the local-index strategy. ([Search with permissions](https://openfga.dev/docs/interacting/search-with-permissions))
- **Label/usage-right enforcement at generation.** Microsoft 365 Copilot checks the EXTRACT usage right on encrypted labeled items before returning their content in answers. ([Purview sensitivity labels](https://learn.microsoft.com/en-us/purview/sensitivity-labels))

**Mapping to this platform's three projections.**
- *Vector (top-k retrieval):* pre-filter with index-embedded audience keys (tenant/space/site/group-set), then **batch-check the top-k×margin candidates** against the decision service before returning — the search-then-check pattern ([OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)), identical in shape to Azure's permission filters ([Microsoft](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)).
- *Graph (multi-hop traversal):* per-node checks during traversal, or traversal restricted to an audience-scoped subgraph maintained from the tuple changes feed (local-index pattern — [OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)). Note graph answers can leak through *edges* (a relationship between two restricted entities is itself knowledge), analogous to Postgres's documented covert channels through referential-integrity checks ([PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)) — edges must carry the intersection of endpoint policies.
- *Wiki (page render):* single `check` per page view plus link trimming, mirroring Confluence's own behavior (links to non-viewable spaces hidden; restricted-content links render as access-denied — [Atlassian](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/)).

## 5. Recommendations

**R1 — Adopt a three-layer common policy object per canonical knowledge asset.**
1. **Normalized effective-access tuples** (subject–relation–resource, usersets for groups/containers, tenant-scoped public): covers every "clean" row of §3. Store in a Zanzibar-class engine (OpenFGA/SpiceDB) rather than a bespoke store — the model, the group-expansion problem, and the consistency tokens are already solved there ([Zanzibar](https://www.usenix.org/system/files/atc19-pang.pdf), [OpenFGA](https://openfga.dev/docs/concepts), [SpiceDB](https://authzed.com/docs/spicedb/concepts/caveats)).
2. **Attribute overlay**: sensitivity/classification labels, expiries, discoverability flags, and restriction predicates, carried as resource attributes/conditions and evaluated at query time by a policy layer with **default-deny and forbid-overrides-permit** semantics (Cedar-style — [Cedar](https://docs.cedarpolicy.com/auth/authorization.html); or OPA with partial evaluation for filter compilation — [OPA](https://www.openpolicyagent.org/docs/latest/policy-performance/)). Restrictions must never be encoded as absence-of-grant: they are intersection semantics and must survive independently of the grant layer (Confluence and Salesforce both structure them this way — [Atlassian](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-on-the-page-level/), [Salesforce](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-sharing-architecture)).
3. **Native-passthrough escape hatch**, declared per asset at ingestion: row-policy-protected tables (Snowflake RAP/secure views, Postgres RLS), possession-link-only content, and encrypted labeled content get an explicit `policy_mode: native` marker. For these, projections may only (a) exclude the content, (b) materialize per-audience slices (the strategy Snowflake itself recommends for high-security views — [secure views](https://docs.snowflake.com/en/user-guide/views-secure)), or (c) federate the query to the source under the end user's identity. Never stamp them with the ingestion service account's effective access.

**R2 — Preserve source policy provenance verbatim alongside the normalized form.** Keep the raw permission payloads (Graph permission resources with `inheritedFrom`, Drive `permissionDetails`, Confluence restriction lists, Salesforce share rows with `rowCause`, Snowflake/Postgres policy DDL) versioned with the canonical asset. This is what makes lossy mappings auditable and re-derivable when the mapping improves, and it is cheap: every source exposes these as structured API objects (§2 citations).

**R3 — Make every projection query path call one decision service; never re-implement per projection.** The invariant "no projection may weaken source access policy" is only checkable if there is exactly one evaluation semantics. Enforce read checks in vector retrieval (search-then-batch-check), graph traversal (audience-scoped subgraph or per-node check), and wiki render (per-page check) against the same tuple store + overlay engine (§4.2). OPA's decoupling principle applies: enforcement points differ, decisions do not ([OPA](https://www.openpolicyagent.org/docs/latest/)).

**R4 — Bind projection versions to ACL snapshots (zookie analog).** The platform already versions projections (HLD); extend each published projection segment with the ACL-store snapshot token it was checked against, and require query-time checks to evaluate **at least as fresh as** the content version — Zanzibar's content-change-check pattern, which exists precisely to stop old ACLs from governing new content ([Zanzibar §2.4.4](https://www.usenix.org/system/files/atc19-pang.pdf)).
 
**R5 — Build permission-delta ingestion as a first-class pipeline, per source.** Concretely: Graph driveItem delta with `Prefer: hierarchicalsharing, deltashowsharingchanges` (budget for the Sites.FullControl.All requirement — [Graph](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)) plus users/groups delta with `$select=members` ([Graph](https://learn.microsoft.com/en-us/graph/delta-query-overview)); Drive `changes.list`/`changes.watch` re-poll loops ([Google](https://developers.google.com/workspace/drive/api/guides/manage-changes)); Salesforce share-table reads accepting platform recalculation lag ([Salesforce](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)); scheduled re-crawl for Confluence (no delta feed found — §2.3); catalog polling for Snowflake/Postgres (§2.4–2.5). Publish a **revocation-propagation SLO** per source and fail closed when a source's feed is stale beyond it.

**R6 — Resolve principals into one identity spine before normalizing.** Sources key principals differently (Entra object IDs and SharePoint site users — [Graph](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0); Drive email-keyed users/groups with tombstoned `deleted` grantees — [Google](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions); Salesforce user/group IDs — [Salesforce](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_bulk_sharing_understanding.htm); Snowflake roles that are *session-activated*, not static user properties — [Snowflake](https://docs.snowflake.com/en/user-guide/security-access-control-overview)). Glean's requirement that users/groups/memberships be indexed before documents reference them is the working precedent ([Glean](https://developers.glean.com/api-info/indexing/documents/permissions)).

## 6. Open Risks

1. **Group-expansion staleness (the new-enemy problem).** Effective access flows through nested groups everywhere (§2); a stale expansion re-admits removed members. Zanzibar treats this as the central correctness problem and solves it with external consistency + zookies; it also needed a dedicated index (Leopard) just to keep deep nesting fast ([Zanzibar](https://www.usenix.org/system/files/atc19-pang.pdf)). Any home-grown expansion cache will face both problems. Mitigation: R4/R5; treat group-membership deltas as security-critical events, not metadata.
2. **Link sharing.** Tenant-scoped (`organization`) links can defensibly normalize to tenant-public tuples; `anonymous` links cannot be represented identity-wise at all, and org default-link configuration changes the meaning of API calls that omit scope ([createLink](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink?view=graph-rest-1.0)). Risk: silently converting possession-based access into identity-based access in either direction (over-grant or over-restrict). Requires an explicit governance decision per scope value (§3 escape hatch).
3. **Deny rules bypassed by union-only stores.** If restrictions (Confluence, Salesforce restriction rules, Postgres restrictive policies) are modeled as missing grants, any later grant re-opens them. The overlay must be evaluated as intersection *after* the grant layer, always (Cedar's forbid-overrides-permit is the reference semantics — [Cedar](https://docs.cedarpolicy.com/auth/authorization.html)). Watch the performance cliff: exclusion/intersection relations are documented as more expensive in list-objects-style queries ([OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)).
4. **Service-account over-collection.** Permission scanning requires elevated app permissions (Sites.FullControl.All for SharePoint permission processing — [Graph](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)); Snowflake row policies evaluated under an ingestion role expose exactly that role's slice as if it were "the data" ([Snowflake](https://docs.snowflake.com/en/user-guide/security-row-intro)). The projection layer must never default to the ingestion identity's effective access; assets lacking a resolvable audience must fail closed.
5. **Row-policy snapshot decay.** Any materialized per-audience slice of RLS/RAP-protected data is correct only at extraction time; mapping-table entitlements change at data velocity (§2.4). Slices need TTLs tied to the source-poll cadence and provenance stamps identifying the role/session context used.
6. **Label enforcement asymmetry.** Labels are readable clear-text metadata, but their *enforcement* configuration (usage rights, priority order, policy assignments) lives in the source's admin plane and changes without touching the document ([Purview](https://learn.microsoft.com/en-us/purview/sensitivity-labels)). Carrying the label ID is not enough; the overlay engine needs a synchronized copy of label→policy semantics, and encrypted content needs an explicit rights strategy before ingestion.
7. **Confluence permission-delta gap.** No permission-change feed was found in the Atlassian documentation reviewed (§2.3). Until verified otherwise, Confluence revocation latency equals crawl cadence — size the SLO accordingly or seek an events product (to be verified in implementation).
8. **Semantic booby traps in source models.** Documented behaviors that will surprise a naive normalizer: Salesforce manual shares silently deleted on owner change ([Salesforce](http://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)); Elasticsearch-style OR-of-roles disabling DLS when any role is unrestricted ([Elastic](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level)) — the same hazard exists for any multi-source principal with mixed grants; Drive discoverability vs access (§3); Confluence space admins who cannot *view* restricted pages but can remove the restriction ([Atlassian](https://support.atlassian.com/confluence-cloud/docs/what-are-confluence-cloud-permissions-and-restrictions/)) — administrative reach must not be normalized as read access.
