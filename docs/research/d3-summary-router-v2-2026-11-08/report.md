# #174 報告：d3-flash 當 summary verify 的 router（v2，ultra 的下限）

**結論：d3-flash 在 held-out 沒有達到 B2。** 選中的規則（G，`t_route` = 0.977）跳過 54% 的 verify 單位、省下 summary 總 token 的 30%。代價是：LLM 標過、經複核確認的 45 句自然錯誤中，有 7 句（15.6%，Wilson 95% 7.7–28.8%）落在被跳過的單位，不會再送到 LLM。B2 的上限是 5%。

即使直接在 held-out 上挑最好的門檻：

- 要把放過控制在 5% 以內，最多只能跳過 14% 的單位，低於 B3 的 30%；
- 要跳過 30% 以上，就得容許放過約 10%。

所以失敗不是門檻選錯，而是 flash 對真實錯誤的分辨力不夠：held-out 自然錯誤的 AUROC 是 0.83，植入錯誤是 0.97。

事後補跑的針對性問題也救不回來（§2.4）：T、M 在 dev 門檻上放過 18–20%；就算在 held-out 上挑最好的門檻，放過 ≤ 5% 時也只能跳過 24%。

**這不代表 d3-ultra 也不行。** B1 當初就定了：flash 是下限，正面結果可以外推，負面結果不行。建議見 §3。

登錄與方法見 [freeze.md](freeze.md)，偏差見 §4。數字來源：

- [selection.json](selection.json)：dev 的選擇；
- [metrics.json](metrics.json)：held-out 的登錄結果；
- [review-dev.json](review-dev.json)、[review-heldout.json](review-heldout.json)：複核；
- [accuracy-heldout.json](accuracy-heldout.json)：植入與 LLM 判決；
- [heldout-corpus.json](heldout-corpus.json)：held-out 語料。

## 1. 量了什麼

這次照使用者 2026-11-07 的裁定重新設計（B1 本機 flash 當 ultra 的下限；B2 容許放過 5%；B3 dev 跳過率 ≥ 30% 才建 held-out）。與 #166 的主要差別：

- **以自然錯誤選門檻**：門檻依「LLM 標過、經 Claude Fable 5.1 盲判確認」的自然錯誤選，不再用植入錯誤。
- **更多問題與規則**：加了四個針對性問題（因果 C、範圍 S、限定詞 Q、主體 E），比較三個規則：G、T = 1 − max(C,S,Q,E)、M = min(G,T)。
- **比較 state 格式**：JSON 與純文字。
- **請求形狀**：每個證據一個請求，也就是 ultra 只讀一次 state 的形狀。
- **held-out 換成新論文**：20 篇 2026-07..10 的 arXiv 論文，分層同原語料，用目前 dev 的 summary 程式跑 Seam B 與 t5b-accuracy。

## 2. 結果

### 2.1 dev 的選擇

| | dev |
|---|---|
| 格式（G 的 AUROC） | JSON 0.955 vs 純文字 0.946 → JSON |
| 自然錯誤（確認且 LLM 標過） | 29 句；允許放過 ⌊0.05·29⌋ = 1 |

dev 的 G：自然錯誤 AUROC 0.928，植入錯誤 AUROC 0.962，植入錯誤的 d3 recall 124/131。

### 2.3 被放過的 7 句

全都是細微的語氣或範圍錯誤，數字和主體都沒錯：

- 原文用 "can"、"may" 的推測，被寫成肯定句；
- 原文說「contributed to」提升，被寫成「造成」提升；
- 原文說是最大占比但未過半，被寫成「大多數」；
- 原文說 6 個中有 5 個，被寫成「全部」；
- 原文說「能力有限」，被寫成「不能」；
- 原文說只有其中一項修改不動其他程式，被寫成三項都不動；
- 原文的節省比例只指學習階段的 token，被寫成沒有限定的 token 總量。

這些正是針對性問題 Q、S 設計要抓的錯。但 dev 上 T、M 規則跳過得比 G 少，所以選了 G，test 只問了 G。這件事看 §2.4 的事後分析。

### 2.4 事後：held-out 加問 C、S、Q、E（不在登錄裡）

登錄結果 commit 之後，才在 held-out 上補問 C、S、Q、E（[explore.json](explore.json)，`explore.py`）。這是事後分析，不改變 §2.2。

| 規則 | dev 的門檻 | 跳過 | 自然錯誤仍送到 LLM | 自然 AUROC | 植入 AUROC | 省下總 token | held-out 上最好：放過 ≤ 5% 時跳過 | 放過 ≤ 10% 時跳過 |
|---|---|---|---|---|---|---|---|---|
| G（選中） | 0.977 | 54.4% | 38/45 | 0.831 | 0.966 | 30.1% | 14.1% | 37.1% |
| T | 0.911 | 48.9% | 36/45 | 0.837 | 0.980 | 27.3% | 24.3% | 31.3% |
| M | 0.911 | 48.7% | 37/45 | 0.842 | 0.980 | 27.1% | 24.3% | 31.3% |

- **針對性問題沒有換來更好的取捨**：在 dev 的門檻上，T、M 跳得比 G 少，放過的自然錯誤反而更多。
- **G 放過的 7 句，T、M 只救回 3 句**，同時放過了別的句子。
- **在最寬鬆的算法下才看得到差異**：放過 ≤ 5% 時，T、M 的 24% 好過 G 的 14%，但這是拿 held-out 自己挑門檻，而且仍低於 30%。
- 自然錯誤的 AUROC 三個規則都在 0.83–0.84，所以問題組的寫法不是主要限制。

### 2.5 複核

| | dev | held-out |
|---|---|---|
| LLM 標過的句子，Fable 判為不受支撐 | 29/67 = 43% | 45/96 = 47% |
| 誘餌（LLM 沒標），Fable 判為不受支撐 | 1/82 = 1.2% | 3/96 = 3.1% |
| #166 盲評的 15 句（只用於 dev 的 AUROC） | 4/15 | — |

- **Fable 比 LLM verify 寬**：Sonnet 5.5 標過的句子中，Fable 只確認了不到一半。這可能是 verify 本來就偏嚴，也可能是 Fable 偏鬆，這次沒有人工複核可以分辨。
- **誘餌的比例低於 #166 推估的 8.6%**：#166 用 Opus 盲評，推估已交付句子中約 8.6% 不受支撐。這次的誘餌比例（1.2%、3.1%）比較低，跟「Fable 比較寬」的解讀一致。
- 複核的 reviewer 自己也回報了幾個「嚴格讀法才判錯」的邊界案例。所以 45 句裡有一部分本身就有爭議。

## 3. 建議

**不把 d3-flash router 放進 summary。** B2 是事前定的標準，登錄的結果沒有達到，事後也找不到能同時滿足 B2 和 B3 的門檻或規則。#135 不必再等本票。

**「是不是實驗設計的問題？」** 這是這次重做要回答的問題。#166 可能的設計問題都檢查過了：

| 懷疑 | 這次的做法 | 結果 |
|---|---|---|
| 植入錯誤不像真錯 | 以複核過的自然錯誤選門檻 | 真錯確實比較難（AUROC 0.83 vs 0.97），但用它選門檻也沒過 |
| 「一句都不能放過」太嚴 | 容許放過 5% | 仍然沒過 |
| 問法不對 | 加上四個針對性問題、三種規則 | 沒有改善（§2.4） |
| 輸入格式或請求形狀不對 | 比較 JSON 與純文字；每個證據一個請求 | JSON 略好，差距很小 |
| 門檻選得不好 | 直接看 held-out 的曲線 | 最好的情況也達不到 |
| dev 的論文太特殊 | held-out 換成 20 篇新論文 | 跳過率很穩（58% → 54%），但放過率比 dev 高 |

所以在這些範圍內，答案是 flash 的分辨力不夠。**還沒排除的只有兩件事**：標註本身的雜訊（全由 Claude 判，沒有人工複核），以及換成 ultra 之後的表現。

**d3 不是沒有訊號。** 它能分辨 LLM 標過的句子：Fable 確認的 45 句有 84% 會送到 LLM，Fable 不認為有錯的 51 句只有 51%（25 句被跳過）。它對明顯的錯也很好（植入 AUROC 0.97）。弱的是語氣和範圍這類細微錯誤。

**需要使用者決定的兩件事：**

1. **要不要量 d3-ultra。** 我建議要，因為 PROD 就是部署 ultra，而這次已經備好整套資料：dev 與 held-out 的請求、標註和評估程式都能直接重用，只要換模型重跑。卡點是硬體：這台 Mac 跑不動 bf16，INT4 只在 CUDA 上驗證過。公司的 GPU 環境是正途；公開的免費 API（`app.vllm-sr.ai`）限研究用途且會記錄請求，這些又都是公開論文，也許可行，但用在公司專案是否符合條款要你判斷。沒開新票。
2. **5% 這條線要不要重新考慮。** 這不是我的建議，只是提供判斷用的數字。t = 0.977 這個點是在 held-out 上量到的：跳過 54%、省下總 token 30%、放過 15.6%（7.7–28.8%）。換成絕對數量：20 篇、984 句，router 多放過 7 句。而 LLM 沒標的 888 句，依誘餌的 3.1%（1.1–8.8%）推估本來就有約 28 句（9–78 句）不受支撐，已經會被交付。所以 router 大約讓交付的錯誤多四分之一，區間很寬。門檻不能帶到 ultra 或 PROD，所以就算放寬，部署時還是要重新校準。

## 4. 偏差與修正（都在看到相關結果之前，除非另外註明）

1. **router.py `labelled()`**：被複核確認為錯誤的 t5b 原句，算成錯誤而不是正確。dev 有 2 句，都來自 #166 的盲評。這是在讀到格式與選擇的分數之前改的。
2. **不問 N（數字與比較）**：#166 的 G 對植入的數字錯誤已經 recall 100%。這是在 freeze 時決定的，記在 freeze.md §4。
3. **held-out Seam B 不跑 d3-check@1**：#161 之後 DEV profile 多了 d3 Quality Check，但 t5b-seam-b 的 runner 不會起 d3 worker，第一次 run 卡在 `check` activity。check 在 summary 之後才跑，summary 不讀它。改用拿掉 check 的 profile 副本（`seamb_heldout.py`）。
4. **paper 11 遞補**：原 paper 11（2610.41245）的 summary 回了 `SCHEMA_INVALID`。照 §7 由 memory 分層的下一篇（2610.38318）遞補。t5b-accuracy 原本在 19 篇上已經跑過一次，遞補後重抽 20 篇的 100 句。這時還沒有任何 held-out 的 d3 輸出。舊結果保留在 `~/archive/research/174-heldout/superseded/`。重抽的第一次 run 因 judge 回了格式錯誤的 verdict 而中止，重跑一次就成功了。
5. **inputs.py 的 re-verify 計數**：#164 之後，不成句的改寫直接丟掉、不再 verify，舊規則卻把它算成一次 re-verify。這是 paper 2 的 verify 呼叫數 assert 抓到的。
6. **事後修正：token 模型的 repair 重送**。#164 會把退化的 repair 答案重送一次，held-out 有 3 次（paper 2、12、15）。#166 的 token 模型要求「repair 呼叫數 = 改寫句數」，所以 `fold_resends()` 把重送併進呼叫數，token 保留在總數裡。這是 test 之後才發現的，但只影響 token 模型，不影響規則、門檻或標註。
7. **事後分析（§2.4）**：在登錄結果 commit 之後才跑，不改變登錄的結論。
8. **freeze.json 的一個欄位**：`dev/review/key.json` 的 hash 從 `files` 移到 `review_answers_sha256`，在發布前改寫了分支的每個 commit，因為 gitleaks 會把這個路徑加 hash 判成金鑰。值沒變，所有 run 都是在原本的檢查下啟動的。

## 5. 限制

- **dev 的錯誤太少**：dev 只有 29 句自然錯誤，允許放過 1 句，所以門檻本身就不穩。不過 §2.2 的曲線顯示，換門檻也達不到要求。
- **dev 偏樂觀**：問題組參考了 #166 看過的錯誤（freeze.md §10）。dev 的自然錯誤 AUROC 0.93，held-out 是 0.83。
- **評審全是 Claude**：verify 是 Sonnet 5.5，複核是 Fable 5.1，沒有人工複核。LLM 的判決也有雜訊（#164），所以「LLM 抓得到的錯」這個集合本身就不穩定。
- **flash 的結果不代表 ultra**：flash 每題各自一次 forward。門檻、分數分布和延遲都不能直接帶到 ultra 或 PROD（ADR-0011）。
- **只量了論文**。

## 6. 檔案

repo 只放計數、分數摘要和不含文字的指標。論文、摘要、複核包與判決、d3 的分數都在 `~/archive/research/174-d3-router-v2/` 和 `~/archive/research/174-heldout/`。

所有 run 都在 `kp_processing` 改名之前的 tree 上跑（#176 之前）。程式維持實際跑的版本，`freeze.json` 的 hash 才對得上；要重跑，把 `review.py` 和 #166 程式裡的 import 改成 `kp_canonicalization`，或在改名前的 commit 上跑。

核心數字（跳過 343/630、放過 7/45、兩個 AUROC）另外不經 `router.py`，直接從原始分數和標註重算過，結果相同。費用：Seam B USD 7.34，加上 t5b-accuracy 的判決與植入，總計約 USD 10，在 USD 15 的上限內。
