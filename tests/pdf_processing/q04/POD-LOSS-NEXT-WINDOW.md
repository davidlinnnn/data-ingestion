# Q04 remaining in-flight Pod-loss qualification

BE proves worker **process** drain/recovery. It does not prove Kubernetes Pod loss: the Q04 trial coordinator and Activity worker ran inside the same Pod. Deleting that Pod would kill the coordinator and prevent it from observing recovery. R3 used a separate coordinator plus a replaceable Activity Pod; its old Pod disappeared 32.1 seconds after deletion and exact native work recovered. Those durations are observations, not new Q04 thresholds. The existing historical `coordinator` Pod has neither the Q04 evidence PVC nor `kubectl`, so it can remain a health endpoint but cannot safely host the Q04 drain driver without altering its Pod spec or losing continuous shared evidence. Use a **new run-owned coordinator Pod** instead.

## Execution design

1. Keep the 32 held Deployments at their exact zero replica values. Use the existing kind, namespace, node and Temporal/object services after rechecking health and absence of running workflows. Create **two run-owned Pods** on the same node: an independent coordinator and a replaceable Activity worker, both mounting a new run-specific evidence PVC. Project the frozen AH producer and current-v3 oracle by exact source hashes; do not alter the historical T09a coordinator, ConfigMaps or directories.
2. The host controller owns Kubernetes injection and evidence. The coordinator Pod submits and queries the native Temporal workflow; the Activity Pod runs the same current-v3 worker/child path. Start independent 250 ms worker-Pod cgroup/process samplers before request admission and retain old/new Pod traces separately. Retain the existing node PSI, OOM, available-memory floor, per-Pod 4 GiB resource gate, telemetry-gap and finite deadlines. The intentional deleted-Pod interval must be an explicit, bounded replacement transition, never an ordinary missing sample treated as complete coverage.
3. Wait for five **durably registered** pages, record their readable artifacts and the in-flight group, then delete only the exact run-owned Activity Pod using UID preconditions. Verify old Pod/CRI container/scratch absence. Admit only one new Pod UID with zero restarts, start its sampler and worker, then require Temporal completion, 51/51 pages, seven components, pages 6–10 at attempt 2 and all prior checked groups retained. Compare the exact frozen document and full graph hashes; independently read every retained object and terminal-inventory member.
4. Fail closed on any mismatched UID, missing or stale sampler, PSI/OOM/memory guard, wrong Activity retry, incomplete business result, hash difference, missing old-runtime cleanup or deadline. One new identity, one run, no automatic retry. Preserve all failed evidence and PVC/object prefix. Remove only run-owned objects with UID preconditions, return Temporal to idle and check service health and the 32 held Deployments.

The BF coordinator/host mailbox and two-Pod runner have local tests for exact run/generation/Pod UID, bound worker readiness/sample hashes, the in-flight parser hold, guard-trigger sample persistence, cancellation before Pod mutation, deleted-Pod all-sample resource checks, replacement-Pod emptyDir input staging and cleanup of the coordinator after an Activity cleanup failure. Worker proof and parser hold use the already-running Activity supervisor and shared-PVC mailbox; no new `kubectl exec` enters an Activity Pod after its collector starts. The collector shares the existing producer lifecycle lock with its worker. A direct node-Python observer samples the exact object Pod UID/container cgroup every 250 ms; a read-only idle smoke produced nine complete samples and an exact remote-process stop. The runner also has all-prefix object readback after business completion. Its one authorized BF live window has now stopped before Pod loss; the runner is locked again (`runtime_authorized=false`). Treat BF as failure evidence, not a Pod-loss pass.

## Current operating-state decision

The temporary 768 MiB MinIO trial was restored to its original 512 MiB limit after BE. BE's exact MinIO cgroup still recorded eight `memory.events max` events and 16.095 ms of full PSI under 768 MiB, although the outer node PSI guard did not fire. A new Pod-loss runner must review object-service memory behavior and its temporary capacity setting before runtime; neither 512 MiB nor 768 MiB is a demonstrated supported bound. Do not weaken the node/Pod PSI or attribution gates to force a pass. The split coordinator and two-Pod telemetry contract now exist and pass their local checks, but no in-flight Pod-loss claim is available for #51 or #44 until one live window completes its unchanged gates.

A locally tested trial in `sentinel/object_limit_trial_bf.py` runs one bounded window with the shared `objects` Deployment at 1 GiB, then restores 512 MiB. It fences the exact Deployment UID and resource version, waits for one healthy replacement Pod, and has regression checks for patch responses lost after the change took effect. The 1 GiB value is a trial setting, not an established safe operating bound: BE's 768 MiB peak was 805,036,032 bytes, only 270,336 bytes below its limit, and its max/full-PSI counters rose. The observed node MemAvailable was about 7.3 GiB before this proposal; remeasure immediately before execution. The user specifically authorized this one temporary shared-service limit change and restoration after automatic approval review had rejected the prior general authorization as insufficient. The BF runner now enters the trial only after verifying held Deployments and idle service health, and attempts restoration in its terminal cleanup on every outcome. Local BF tests and two-axis review passed before enabling one live window; unchanged resource and business gates remain in force.
