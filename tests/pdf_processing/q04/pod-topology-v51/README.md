AY showed MinIO container-full PSI and `memory.events max` rising with node-full PSI while the container was within 372 KiB of its 512 MiB limit. Its anonymous memory grew while file cache was reclaimed. The exact request causing the burst remains unknown. AZ tests one variable: the existing `objects` Deployment's container memory limit is temporarily 768 MiB instead of 512 MiB. The request remains 128 MiB; image, object PVC, node, frozen AH producer, current-v3 oracle, Q04 worker topology, node PSI zero limit, Pod/cgroup guards, deadlines, cleanup and one-run/no-retry policy are unchanged.

The Deployment UID is `9e69720a-ff80-4aa5-9941-14925dfdf981`; its previous JSON was saved to `/private/tmp/q04-objects-before-az.json`. The UID- and old-value-fenced patch rolled out one ready `objects-6756bf97c6-pkqb7` Pod, UID `a84384de-8292-439e-b8ce-d75a70816d3f`, on worker2 with a 768 MiB limit and no restart. The host observer checks that exact Pod UID, container cgroup and limit throughout AZ. All historical Q04 PVCs/prefixes are retained.

Prediction: if the 512 MiB cgroup limit is a major cause of the AY node-pressure burst, AZ should avoid `memory.events max` and MinIO/full-node PSI at the corresponding workload stage while still passing every unchanged Q04 guard. A clean AZ pass would prove only the process-drain row under this operating configuration; it would not prove the precise MinIO operation, Pod drain/recovery, or #51 closure. A failure stops without retry. After terminal evidence is sealed, review whether to retain the 768 MiB limit as an explicit operating bound or restore 512 MiB with a UID- and value-fenced patch; do not silently treat the trial setting as a permanent accepted bound.
