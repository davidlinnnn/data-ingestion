# BF Activity-Pod memory-policy inheritance diagnosis

BF stopped on simultaneous node and Activity-Pod full PSI during native warm-parser growth, before Pod-loss injection. Comparing the first eight seconds after native workflow start gives a useful control: BE (successful worker-process drain) reached 1,235,505,152 cgroup bytes and 1,118,896,128 warm-parser PSS without full PSI or direct reclaim; BF reached 1,139,519,488 cgroup bytes and 1,209,376,768 warm-parser PSS with full-PSI avg10 0.18 and 19,501 new node `pgscan_direct`. BE's minimum node MemAvailable was 5,923,745,792 bytes, **lower** than BF's 6,339,411,968 bytes. BF also recorded 348 node `thp_fault_alloc`, 58 `allocstall_movable` and 181 `compact_stall` increments in that interval; BE recorded 10, 0 and 0. Memory amount alone does not explain the stop. Node counters are not per-process attribution.

Both runs' `workload-memory-policy.json` say `THP_DISABLE=1` and `inherited_by_children=true`, but those files were written by their **coordinator** supervisors. BE ran coordinator and Activity child in one Pod/process tree. BF moved its Activity supervisor to a separate Pod launched by a fresh `kubectl exec`; `pod_activity_supervisor_bf.py` did not call `PR_SET_THP_DISABLE` before spawning `worker_bc.py` and the warm parser. An isolated fresh exec in the same runtime image read back `PR_GET_THP_DISABLE=0`. An isolated process that called `PR_SET_THP_DISABLE` read back 1, and its exec child read back 1. This identifies a real topology-induced memory-policy inheritance gap. It makes THP/compaction a strong causal hypothesis for the BF PSI burst, but the retained trace did not read the historical warm parser's own THP flag, so that precise causal link remains unproven.

The local correction applies the already-used `pod_workload_p.disable_thp()` inside each BF Activity supervisor before starting its collector or worker and durably records `activity-memory-policy.json` for that generation. The regression drives the real Activity supervisor startup seam: before the fix, the worker-spawn hook found no policy evidence; after the fix, the policy is present before spawn. The existing Linux helper performs `PR_SET_THP_DISABLE` followed by `PR_GET_THP_DISABLE` readback; it changes no node sysfs setting. The BF runner remains locked, so no historical identity is rerun. A future new-identity window must verify Activity policy readback, process/cgroup/node samples, and the unchanged zero-PSI guard before claiming Pod-loss acceptance.
